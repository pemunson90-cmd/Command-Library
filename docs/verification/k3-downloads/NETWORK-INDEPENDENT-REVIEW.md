# Independent bounded transport review

Reviewed 2026-10-12: `Command-Library-network/android-app/data/network/.../UrlConnectionNetworkClient.kt`, its 14-test source suite and `coordination/handoffs/cx-k3-network-01.md` for author commit 11e0a01. Read-only review; no repository edits, compilation, tests, external requests, TLS or physical-device execution by this reviewer. Author-reported JVM results remain separate evidence.

**Disposition: do not bind this implementation as the production transport yet.** Its origin checks, explicit raw representation and no-replay-after-emission design are useful, but the 500 ms connection/header cap sacrifices ordinary mobile usability. Passing fast local cancellation tests does not resolve that tradeoff.

## Concrete blockers and smallest fixes

1. **Configured timeouts are replaced by 500 ms before connection/header acquisition (lines104–116).** Both connectTimeout=15s and readTimeout=30s become500ms. A valid response with headers arriving after700ms fails; safe retry repeats the same failure rather than allowing the configured budget. TLS setup also inherits platform socket timeout behavior. This is not production-fit for the full English crawl. Remove these hard caps and use a transport whose call cancellation closes active sockets without imposing a short ordinary I/O deadline. An explicitly configured OkHttp Call is a reasonable small replacement, subject to dependency compatibility and actual tests; swapping the dependency alone is not acceptance. Keep finite configured connect/read/write/call budgets and preserve the core NetworkClient signature. Do not simply raise the500ms cap and silently lose the required cancellation behavior.

2. **Cancellation guarantees are narrower than the API/hand-off requirement.** Monitor line70 synchronously invokes potentially blocking disconnect before token cancellation; cleanup also invokes disconnect and joins the NonCancellable monitor. A500ms socket read backstop is not a bound on DNS resolution, request-body writes or platform TLS behavior. No write timeout is configured. The14tests exercise a loopback server that has already sent headers and one body byte; they do not establish cancellation during DNS, connect, headers, TLS or a blocked upload. Replace the disconnect-monitor mechanism with cancellation-aware call ownership, promptly cancel the coroutine/token path, and ensure cleanup cannot wait indefinitely for a blocking disconnect. If shared transport supports POST bodies, provide a finite write budget and verify no automatic replay; otherwise reject unsupported methods explicitly until implemented. DNS lifetime/cancellation needs a documented bounded strategy or a narrowly stated limitation verified against requirements; do not claim that OkHttp automatically makes every platform resolver interruptible.

3. **Retry-After above24hours is silently discarded (retryAfter helper).** Valid `Retry-After: 172800` returns null. The retry loop can then retry after its short backoff (or30s for Scryfall429), violating the stated rule that a longer server interval is never shortened. A valid HTTP date more than24hours ahead has the same defect. Parse valid durations/dates without treating an oversized positive value as absence; if it exceeds the finite call/retry budget, stop with a typed budget failure and preserve the required cooldown policy. A bounded, saturating representation or explicit exceeds-budget parse result avoids overflow. Strictly consume an entire HTTP-date value. Add the172800s and >24h-date tests; the current120s over-budget test cannot detect this bug.

4. **Continuing the same InputStream after every SocketTimeoutException is not a portable recovery guarantee (readBounded).** HttpURLConnection implementations can treat timeouts as terminal, and chunked framing or TLS implementations need not preserve resumable parser state after a timeout. The supplied tests never prove a healthy body resumes after a pause longer than500ms. Eliminate routine timeout-and-continue polling when replacing transport: use the configured idle timeout normally, fail a timed-out stream without emitting final, and let durable acquisition resume/restart through its validated source protocol. Confirm that an ordinary750ms body gap succeeds with readTimeout=30s and a real idle timeout fails without final or internal replay.

## Security and boundedness follow-through

The explicit HTTPS origin allowlist, userinfo/fragment rejection, manual five-hop redirects and stripping all non-public headers across origins are sound at the adapter boundary. Secret references fail closed; errors avoid URLs/bodies/credential text. A replacement must preserve these properties. Disable automatic redirects, implicit authentication/cookies/cache and hidden connection retries/replays, or establish their precise equivalence to the contract. HttpURLConnection may participate in process-global CookieHandler/Authenticator behavior; filtering the explicitly supplied header list alone is not proof that every transmitted credential is origin-scoped. Existing tests cover only explicit request headers.

The response-header limit is checked only after responseCode/header parsing and only for2xx responses. It bounds the exposed success DTO, not memory allocated while parsing redirect/error headers. Pin a transport with a finite parser header budget and apply metadata validation uniformly to success, redirect and retry/error paths. Request/response string limits currently count UTF-16 code units, not serialized bytes, and a map-size bound is not a bound on repeated header-value count. Preserve a finite wire/parser limit and separately cap total header entries before flattening. These are bounded transport implementation details, not grounds for a large framework.

Finite positive timeouts should explicitly reject Duration.INFINITE: the existing core RequestSpec/RetryPolicy guards and this constructor's `> ZERO` checks admit it. The default finite maximumOverallTimeout helps normal calls but is itself caller-replaceable. Overflow-safe deadlines/backoffs are needed before labeling arbitrary configurations bounded.

Source scheduling remains a higher-layer obligation: this adapter's2/s Scryfall search cap is500ms, whereas the reviewed acquisition policy requires sequential starts at least600ms apart; bulk metadata needs10/min. Keep the already planned acquisition-layer controls and shared Scryfall429 cooldown. Tests with a synthetic host rewrite are rate-policy unit evidence, not live Scryfall or TLS proof.

## Focused acceptance for the replacement

Retain the useful existing tests: contiguous bounded chunks, raw gzip, truncation/no final, origin redirects/credential stripping, safe retry rules, no replay after any emitted byte, Retry-After, shared cooldown and close. Add slow successful headers/TLS/body gaps within configured budgets; coroutine and token cancellation while awaiting headers and body, plus connect/DNS/write behavior within supported scope; long Retry-After; and inherited/global credential isolation. Use synthetic fixtures, controlled timing and counters. Run the actual Android implementation on required API lanes for TLS/cancellation; JVM HttpServer cannot establish Android HttpURLConnection behavior or physical mobile performance. Verify library defaults for raw gzip and hidden retries rather than assuming they match this wrapper.
