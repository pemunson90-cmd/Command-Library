# Durable consent removal choice — candidate design

Current settings RevokeConsent ignores removeDownloadedData because the accepted K2 adapter had no downloads. K3 binding must honor that choice across process death, without atomically pretending two independent stores committed together.

Smallest settings-side proposal: StoredConsent gains pendingDataRemoval Boolean, default false for schema1; schema2 binary format writes one explicit Boolean after each stored installation+ConsentRecord. Preserve all old fields/Knowledge/revisions/checksum/size bounds. Decoder accepts exact versions1/2; future versions fail closed. Store candidate validation rejects pending=true unless that exact consent record is revoked. RevokeConsent(remove=true) atomically stores revokedAt plus pending=true in the same DataStore acknowledgment, including an already-revoked consent; remove=false never clears a previously requested removal. No network approval is created. Duplicate requests coalesce by exact installation+consent ID.

Concrete settings adapter adds pendingDataRemovals(cancel):Outcome<PendingDataRemovals> (adapter-local immutable DTO with exact settings Revision and scoped SnapshotList<EntityId>) (read ungated, scoped to current installation and exact revoked record) and acknowledgeDataRemoval(id,expectedRevision,cancel):Outcome<Unit> (shared consent gate + settled DataStore write; compare the current settings revision first, then clear only the exact pending request after successful complete removal; stale acknowledgment changes nothing). Acknowledgment changes the persisted revision/updatedAt consistently; stale ordinary settings patches still commit nothing. Foreign restored records and their pending flags remain inert; corrupt/missing settings fail closed. No core SettingsSnapshot shape change or fake observation API is required.

Root coordinator drains pending requests after startup and explicit revoke, using caller-owned cancellable execution and real job/cache managers. Engine durable pending-removal marker provides raw artifact deletion retry; downloaded installed catalog/rules caches and later resources must be scoped to provenance before acknowledgment. Remove installed caches only on this explicit user choice, preserving decks/collection IDs and user data; automatic artifact deletion alone must not cascade installed content. A single root drainer is serialized, and conditional revision acknowledgment additionally prevents ABA from stale/concurrent drainers. Refresh the snapshot after each acknowledgment/revision conflict. Fence/quiesce exact old-consent writers and readers before deleting. Installed catalog/rules proof persists the immutable acquisition consent ID alongside artifact provenance, so later job cleanup cannot erase removal scope; selected imports have no acquisition consent ID and are excluded. A later distinct consent never belongs to the old request merely because resource URLs match. Ack only after every applicable deletion is durably complete; errors keep request pending and visible, retries idempotent. If canceled after store commit, request remains pending. Do not call a consent-writing operation while already holding the non-reentrant guard.

Required real format/DataStore tests: schema1 preservation and no inferred request; schema2 roundtrip/corruption/future refusal/size bounds; atomic revoke+request across reopen; stale revision no effects; cancellation after serializer boundary retains pending flag and shared gate settlement; revoke false does not clear pending; already revoked true queues; exact acknowledgment/revision and unknown ID rejection; concurrent old acknowledgment versus a newly re-requested removal cannot clear the new occurrence; wrong installation has no pending/removal authority. Root integration tests later prove full installed-cache scope and recovery, not merely serialization.

This design does not change cache defaults/retention consent, add languages, or authorize deletion beyond an explicit recorded removal choice. Independent design review and implementation/runtime verification are pending; no feature acceptance follows.
