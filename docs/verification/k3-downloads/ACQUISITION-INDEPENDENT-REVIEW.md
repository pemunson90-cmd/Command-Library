## Blocking protocol corrections

1. **Consent checking has a race and the referenced observation facility does not exist.** Current SettingsRepository exposes read/update/approve, no observe. Reading durable settings immediately before a job transaction permits revocation to complete before QUEUED or COMPLETED commits; an asynchronous observer alone still permits that interleaving. Smallest fix: one application-scoped coordinator shared by every settings revocation writer and acquisition request-dispatch/commit path. Serialize the authoritative read plus short dispatch/commit handoff against revocation, cancel an already active response when revocation wins, and recheck durable consent on restart. Do not hold this gate for an entire download. All settings entry points, including removeDownloadedData, must participate. State the linearization rule explicitly: revocation before dispatch/commit prevents that action; revocation afterward stops remaining transfer and follows retention/removal choice. Merely adding Flow observation is insufficient. Missing/unknown/corrupt settings must fail closed without creating consent.

2. **Database owner CAS does not fence filesystem writes.** After pause clears owner_token, an old worker can still append or rename its shared partial file while resume starts another worker. Both may hash mixed bytes before one loses its DB CAS. Smallest fix: per-job execution/file exclusion plus cancellation-and-join before a new owner can reuse the partial key, or separate attempt-owned files that stale owners cannot access. Apply the same exclusion to recovery and artifact deletion. Specify that pause/cancel acknowledgment either waits for writer quiescence or prevents resume from acquiring the file until quiescence. Owner/state/revision checks remain necessary for every DB checkpoint. A zero-row update must abort the surrounding transaction, including preceding seen-ID inserts; the existing Database latch does not turn a successful zero-row execute into rollback automatically.

3. **Rename recovery needs a fully durable, unambiguous handoff.** File fsync then rename does not alone guarantee the directory entry survives power loss. Sync the containing directory where supported, and never commit COMPLETED on a platform failure to establish the promised durability. Derive a unique candidate key from persisted partial key plus attempt/owner, or persist it before rename; job ID alone cannot distinguish stale attempts. Recovery must not resurrect CANCELLED/revoked jobs from a candidate file. It may restore the durable partial checkpoint and INTERRUPTED state; publishing a candidate needs the same state/consent/verification guards as ordinary completion. If COMPLETE JSONL provenance cannot be reconstructed after rename, restore and revalidate instead of inventing retrieval metadata.

4. **Transfer-budget semantics across crash/restart are underspecified.** A page-boundary checkpoint can lose the byte accounting for an interrupted page, and resetting attempts must not silently evade a purported job-wide maxTransferBytes. Define limits as per attempt or per job and implement that definition. For a job-wide finite budget, reserve the bounded request allowance durably before dispatch, reconcile actual consumption on success, and conservatively retain the reservation after an ambiguous crash; an equivalent conservative scheme is acceptable. Distinguish durable file offset from cumulative transferred bytes. Explicit retry limits also bound repeated fresh attempts. Progress resetting needs an exposed attempt identifier (small additive snapshot field) or a documented state transition so consumers do not treat every counter decrease as corruption.

## Required small contract clarifications

- Constructors or shared boundary validators must reject invalid source/kind/provider/language combinations, negative Known counts/lengths, wrong hash algorithm/length, inconsistent snapshot state/phase/artifact combinations and overflowing revisions/counters. ResourceUri currently checks only nonblank; ContentHash only nonblank algorithm and hex syntax. Neither provides HTTPS/origin or SHA-256 guarantees. Bound UTF-8 strings, URI, payload, notices/evidence and collection sizes before expensive serialization/allocation. Unknown/Absent metadata must retain their distinction and reason; do not collapse them through nullable SQL fields. All finite policy ceilings need concrete reviewed profiles before production wiring.
- Pin raw file acquisition to explicit `Accept-Encoding: identity` with transparent HTTP decompression disabled, and reject unexpected transport encoding unless explicitly handled. A `.jsonl.gz` file is gzip artifact compression independently of HTTP Content-Encoding. Expected size/hash, Range offsets and artifact bytes must refer to the same representation. If accepting other HTTP encodings, retain that exact encoding in verified provenance as well as the job row. EnglishSearch yields derived uncompressed UTF-8 JSONL; HTTP page lengths/ETags/checksums must not be asserted as validators of those derived bytes. `upstreamChecksumMatched=false` is acceptable for absent or unknown expected checksum but must not erase that Knowledge distinction in the persisted plan.
- Clarify cancellation ordering as a successful CAS/transaction linearization, rather than arrival time of a concurrent cancel method. A cancellation that invalidates owner before completion's CAS wins; a stale cancel racing after completion receives stale/invalid status. Bound noncancellable cleanup and preserve CancellationException propagation.
- Immutable keyset ordering is good; timestamp high-water alone does not exclude newly inserted jobs after clock rollback or same-timestamp random-ID insertion. Either explicitly document live membership (states already are live), or add a durable monotonic insertion sequence/high-water filter. Bind cursor version/order/last-key/high-water and reject malformed cursors. Do not call the result an immutable listing snapshot without that membership rule.

## Approved details and migration boundary

The file-versus-derived-JSONL distinction, first-page digest revalidation, unique producer IDs, source count/page/language checks and NON_ATOMIC_TRAVERSAL label correctly avoid claiming an upstream snapshot. Initial-page equality cannot establish unchanged middle pages; the proposal acknowledges this. Raw file verification is acquisition success, not gzip/parser/catalog validity. openArtifact may emit data before final integrity validation only because the consumer activates on verified final completion; preserve this condition in importer tests. No network grant follows from opening already acquired retained bytes.

The exact three SQL tables and Room entities are structurally consistent with existing conventions: additive v2 migration, private basenames, no foreign key into DataStore, no destructive fallback, owner CAS and durable offsets. Preserve all existing tables/indexes/data and both migration registrations. Actual KSP schema3 export and native migration/reopen/integrity evidence remain future work; this review does not substitute for them.

Nullable contentUri plus explicit input kind/job/provenance is the correct importer contract direction. This is a source compatibility change for property consumers despite defaulted new fields; update every reader/codec/error path together. Prefer the explicit catalog/rules nullable migration at importer integration. If temporarily using the proposed empty-string sentinel, only the new versioned payload decoder may select it; legacy decoders must never parse/display it as a URI. Preserve old payload versions and local content:// imports. Keep the importer metadata change separate from claiming the jobs-only schema finishes K3.

## Root integration resolution

- New acquisition-plan DTO is named DownloadPlan; existing pricing AcquisitionPlan remains unchanged. Real compile caught that name collision before consumer binding.
- Hash algorithm uses existing SHA-256 spelling; snapshot explicitly carries attempt for reset/progress interpretation.
- Production binding must use an application-scoped consent coordinator shared by every settings writer and request/commit handoff. Revocation before dispatch/commit blocks it; afterward cancels remaining transfer. Missing settings fails closed.
- Use per-job execution/file exclusion; pause/cancel invalidates CAS and cancels/joins the writer before acknowledging resumable access. Recovery/deletion share exclusion; zero-row CAS aborts whole transaction.
- Candidate filenames are attempt-owned and persisted before final rename. File and containing directory must be synced before completion; recovery cannot resurrect cancelled/revoked work or invent provenance.
- Limits are job-wide: reserve each bounded request durably before dispatch; successful completion reconciles actual bytes; an ambiguous crash retains reservation. Explicit max attempt counts bound restarts. Live list membership is documented; do not call it a fixed snapshot.
- Schema3 additions are additive infrastructure only; do not claim K3 or full-app completion.
