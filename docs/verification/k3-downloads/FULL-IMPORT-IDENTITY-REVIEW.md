## 1. Canonical comparison correction

The two reported duplicate-Oracle conflicts differ only in keyword order with identical values. Sorting `Knowledge.Known` keyword/color collections for comparison is correct: order is incidental, multiplicity remains significant, and original source order/raw JSON remains stored. Ordered faces and their indices must remain ordered. Missing/null/unknown states must not collapse into known empty, zero, or each other; diagnostic reason/evidence differences need not cause canonical conflicts. The current `sameKnowledge` behavior meets that distinction. BigDecimal numeric comparison and matching digest normalization remain appropriate.

The accompanying sorted digest rendering is consistent with the equality change, but the digest is only a prefilter, never proof of equality. Existing `List.toString()` rendering is not an injective encoding (one keyword containing a comma can render like two keywords). Continue the disk-backed raw-payload decode plus `sameCanonicalGameData` confirmation; do not introduce digest-only deduplication. A future structured digest encoding must be versioned; existing stored digests cannot silently acquire a new meaning. The current root test source covers permutation equivalence, removed/duplicated keywords, and face-order significance; execution was not independently run here.

## 2. Exact identity mapping

The measured artifact contains 116,009 distinct English printing IDs and 38,743 distinct supplied top-level Oracle IDs. Exactly 83 `reversible_card` records lack top-level `oracle_id`. Their 166 faces reference 72 distinct supplied Oracle IDs, all reported already present among the canonical English records. Expected canonical count for these exact bytes remains **38,743**, not an invented increment. Expected accepted printing count is **116,009**, with zero silently skipped rows.

Private field-shape inspection confirmed 83 records/166 faces/72 distinct face Oracle IDs. Face layouts are 158 normal, 2 token, and 6 adventure. All faces supply name, oracle_text, mana_cost, cmc, colors, type_line, layout, and oracle_id; they do not supply per-face keywords, reserved, or color_identity. Never promote a reversible face into a complete `CardRecord` by borrowing the enclosing printing's keywords/color identity or supplying empty defaults. Adventure face content particularly disproves treating each printing side as target canonical face index zero or copying its printing-side index into `FaceIdentity`.

Minimum internal mapper result: a named result with `canonical: CardRecord?` and `printing: PrintingRecord` (plus raw source retained by staging). Existing tiny-path wrapper may retain its `Pair` API for its previously accepted inputs; the bulk path consumes the new result. Rules:

- Ordinary top-level Oracle record: existing canonical mapping and known printing Oracle remain intact.
- `reversible_card` with absent top-level Oracle: `canonical=null`; printing Oracle is `Knowledge.Unknown` with reason that no single whole-printing Oracle was supplied; all three SQL Oracle columns stay null. Preserve printing ID, language, set/collector text, assets, links/vendor IDs and full source object.
- Each reversible `PrintingFaceAsset`, already keyed by actual printing ID and source face index, gets a `FaceRelationship` using existing `OTHER`, `relatedOracle=Known(source-qualified supplied oracle_id)`, `rawRelatedIdentity=Known(ProviderIdentity(provider,"oracle",raw))`. `relatedFace` remains unknown unless independently supplied; `relatedPrinting` remains absent/unknown as appropriate. Do not fabricate a canonical face ID. Evidence may name the source field path without including source prose.
- Do not broaden this exception to every missing top-level ID: unsupported shapes fail explicitly. Do not infer IDs from names, art IDs, or `all_parts` (its IDs identify printings). Retain complete private raw payload so source fields absent from present DTO projections are not lost.

## 5. Bounded framing, hashes, provenance

Bulk input must stream strict UTF-8 JSON_ARRAY or JSONL, compressed NONE or GZIP according to declared framing. Keep chunk sequence/offset/final validation, duplicate-field checks, nesting bounds and cancellation. Full gzip trailer/CRC and no unvalidated trailing content are activation prerequisites. JSONL EOF/blank-line policy must be explicit; never truncate an incomplete last object into success.

Use a versioned finite initial profile with max decoded 2 GiB, max 500,000 records, max record 8 MiB, max chunk 64 KiB and nesting 32; separately cap raw/compressed input bytes. These are proposed safety headroom, **not measured Android performance limits**. The measured English artifact is 620,805,214 bytes; maximum record is 94,377 bytes without LF (94,378 with LF), so it fits comfortably. Define delimiter accounting explicitly.

Normative batch flush threshold is 2 MiB of retained raw UTF-8 records or 1,000 records, whichever occurs first; flush before appending a record that would exceed the byte threshold. There is one necessary explicit edge-case rule: a valid record may be 8 MiB, larger than a 2 MiB batch. Admit it alone through an immediate singleton transaction after flushing the preceding batch, with the 8 MiB record bound, and never co-buffer it with other records. Thus 2 MiB is the ordinary batch budget, not an absolute maximum transaction payload. If the intended contract requires an absolute 2 MiB batch ceiling, it conflicts with accepting 8 MiB records unless the storage write is itself streamed/split; do not conceal that conflict. None of the measured records needs the singleton exception. Raw budget does not prove heap budget: avoid retaining all corpus records or duplicated mapped object graphs.

For GZIP, hash/count exact artifact bytes before decompression separately from decoded bytes. For English search, VerifiedArtifact.hash identifies the derived JSONL, not original page bodies. Preserve requested/final source URI, retrievalStartedAt/retrievalCompletedAt, `NON_ATOMIC_TRAVERSAL`, source version/date Knowledge, declared/observed counts, parser/payload versions and notices. Do not replace the retrieval interval with import time or label stable counts an immutable snapshot. The measured interval is 2026-10-12T22:02:15.519318Z through 22:27:45.728292Z; interruption/resume and absence of immutable snapshot token remain real limitations.

## 6. Activation and recovery corrections

Use existing staging generation and one atomic dataset pointer, with one shared import owner across tiny/bulk adapters. Successful acquisition is not installed catalog success. Never let one adapter's startup cleanup erase the other's live staging generation; either share the existing process mutex/owner or persist ownership for independently scheduled writers.

Before activation validate EOF/final chunk/gzip integrity, raw/decoded expected hashes and sizes, actual SQL row counts, printing ID uniqueness, language, canonical conflicts, required membership target resolution/counts, projection/FTS completeness and current input binding. Snapshot generation identity once per lookup; keep reads/cursors pinned. Perform expensive validation outside the short pointer transaction while staging remains exclusively owned. In the transaction verify staging state/ownership and expected old active pointer, persist verified metadata/counts, retire the previous generation and switch pointer atomically. Do not activate when the final source page/count expectation is incomplete. Check affected-row counts; zero-row updates are not success.

A crash before pointer commit leaves old active data valid. A crash after commit must recover installed success from durable state even if caller/progress notification never received it. Postcommit cancellation/progress failure must never remove active rows. Artifact retention/deletion is separate from installed catalog retention. A retry may create fresh staging from the verified artifact; mid-import resume is not required for this minimum design and must not be implied.

Current LocalCatalog cleanup is a single cascading delete under a 1-second timeout, and initialization blocks lookup until cleanup completes. That is insufficient evidence for a full generation: a large failed import may repeatedly time out and block access to the old active catalog. Mark uncommitted generation failed/abandoned and reclaim its FTS/membership/assets/printing/faces/oracles in bounded, restartable pages, each guarded against the active pointer and live owner; remove generation last. Readers should continue using the old active pointer while cleanup remains pending. If VALIDATED is persisted, startup recovery must handle it as well as STAGING. Old retired generation retention/deletion remains explicit and must never delete user tables or rewrite deck/owned identities.

### Exact AndroidX FileProvider correction

Standard AndroidX `FileProvider.attachInfo` rejects `android:exported=true` and also rejects **`android:grantUriPermissions=false`**, with `SecurityException("Provider must grant uri permissions")`. Therefore “no grants” must mean no grants are issued, not a false manifest flag. Use `exported=false`, `grantUriPermissions=true`, no calls to `grantUriPermission`, no read/write grant flags or grant-bearing ClipData in external intents, and no sharing UI for these URIs. Merely enabling the manifest capability grants access to nobody. If a false grantUriPermissions flag is a hard implementation requirement, use a properly implemented internal ContentProvider instead of AndroidX FileProvider.

Use a dedicated authority and a small FileProvider subclass, with an XML path mapping restricted to the actual completed-artifact directory. Do not expose root-path, files-path `.` or other directories containing databases, credentials, staging files, or unrelated user content. Verify that the chosen FileProvider root actually covers the acquisition store's real directory; standard `files-path` does not automatically encompass every app-private directory. Use opaque private artifact basenames and prevent symlink/path traversal or replacement from escaping the permitted root. A functioning provider must support actual same-UID resolver reads; do not merely concatenate a plausible URI string. Keep URIs out of external messages/logs. These are implementation checks for the requested private binding, not an additional approval gate.

Platform source checked read-only on 2026-10-12: https://raw.githubusercontent.com/androidx/androidx/androidx-main/core/core/src/main/java/androidx/core/content/FileProvider.java (`attachInfo`, URI/path mapping documentation, and `openFile`).
