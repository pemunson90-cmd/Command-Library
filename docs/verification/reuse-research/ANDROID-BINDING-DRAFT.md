## Existing contracts and decisions

- `LocalAcquisition` is internal and implements the existing `DownloadService` and `DownloadRunner`. Its required adapters are `validateTrustedRequest: (AcquisitionRequest) -> Outcome<Unit>`, `endpointFor: (AcquisitionRequest, ResourceUri) -> EndpointProfile`, and `connection: suspend () -> AcquisitionConnection`; do not expose these internal seams to app callers.
- `authorizeWireDispatch(RequestSpec, ResourceUri, CancelToken, () -> Unit)` already uses an identity map of the exact original spec, authoritative job/consent lookup and the shared `ConsentCoordinator`. It validates every actual target and performs synchronous enqueue under the gate. Equal reconstructed specs have no authority.
- `withArtifactFile(jobId, cancel, action: suspend (File, VerifiedArtifact, Flow<ByteChunk>) -> T)` holds the job file guard through **the entire action**, checks durable completion and rehashes the actual file before action entry. Its supplied flow rechecks exact bytes/hash at EOF. Do not call `openArtifact` inside this action: that reacquires the same non-reentrant file guard.
- `CatalogVerifiedInputBinding.withPinnedInput(source, cancel, consume: suspend (Flow<ByteChunk>, EntityId) -> CatalogBulkImportResult): CatalogBulkImportResult` is the actual internal binding contract. Use this signature, without guessed callbacks or return types.
- `CatalogBulkImportSource` already requires a genuine nonnull content URI and, for `VERIFIED_ARTIFACT`, a descriptor plus matching framing/compression/bytes/hash/source metadata. `LocalBulkCatalog` ignores caller chunks for artifact input and runs its entire consumption/activation within the binding callback.
- The authoritative reviews are `docs/verification/k3-downloads/FULL-IMPORT-IDENTITY-REVIEW.md` (including its provider addendum) and `WIRE-CONSENT-DESIGN-REVIEW.md`. Genuine private URI binding/additive schema4 and enqueue-only gating are already approved. Their FileProvider recommendation requires an actual completed-only directory.

## Smallest factory and ownership

Ownership correction after root review: `docs/architecture/KOTLIN_OWNERSHIP_MAP.md:36` explicitly says **"No component imports another component's implementation package"** and permits bootstrap to wire exported factories. `kotlin-registry.json` allows catalog's conceptual network dependency and app's network composition edge, but its current K2 consumed catalog subset is only model/common/storage. A permitted conceptual edge does not authorize importing `OkHttpNetworkClient` from catalog. The earlier direct-composition recommendation was incorrect and is superseded by the following boundary.

Root creates a public, concrete `AndroidCatalogServices` facade in the catalog module's API package (for example `com.architectpsg.commandlibrary.feature.catalog.api`); its constructor is private. Proposed factory uses existing model/common types and **one required function parameter**, with no new core capability or authorizer DTO/interface:

```kotlin
public fun create(
    context: Context,
    database: Database,
    settings: SettingsRepository,
    consentCoordinator: ConsentCoordinator,
    clock: Clock,
    ids: IdSource,
    transportBuilder: (
        suspend (RequestSpec, ResourceUri, CancelToken, () -> Unit) -> Unit
    ) -> NetworkClient,
    bulkLimits: CatalogBulkImportLimits = CatalogBulkImportLimits(),
): AndroidCatalogServices
```

Expose named properties typed as existing `DownloadService`, `DownloadRunner`, `CatalogBulkImport`, `CatalogPrintingLookup`, and `CatalogOracleLookup`. Expose one concrete Android method `catalogSource(jobId: EntityId, cancel: CancelToken): Outcome<CatalogBulkImportSource>` for deriving a genuine bound source. This is an Android facade addition for root review, **not** a new core capability. Keep the engine, transport, provider registry and `CatalogVerifiedInputBinding` private/internal. A later root removal coordinator may need a concrete facade forwarding `removeArtifacts(consentId, cancel): Outcome<Unit>`; its semantics already exist internally, but settle Task4 fencing before publishing that access.

The catalog factory creates `androidArtifactFiles(File(context.filesDir, "acquisition-artifacts"))`, one engine and one bulk importer/identity lookup. It gets exactly one transport by calling the required builder once, supplying its exact authorizer function. Verify no existing production artifact directory is in use before choosing this exact new directory. Preserve keys/layout; no migration is implied by this proposed path.

Close the construction cycle using a private `lateinit` engine captured by the supplied suspend authorizer. The catalog factory calls `transportBuilder { spec, uri, token, enqueue -> engine.authorizeWireDispatch(spec, uri, token, enqueue) }`, then constructs/assigns the engine with the returned `NetworkClient`, then publishes the facade. Production transport construction is inert; invoking the authorizer before assignment fails creation rather than bypassing authorization. Factory/client references cannot escape before successful assignment. No overload/default taking a generic already-created `NetworkClient`.

Only `AppGraph` (root bootstrap) constructs the concrete network adapter. Its exact composition expression is:

```kotlin

    OkHttpNetworkClient(
        clock = SystemUtcClock,
        dispatchGuard = WireDispatchGuard { request, uri, cancel, enqueue ->
            authorize(request, uri, cancel, enqueue)

```

`WireDispatchGuard` remains defined in `data:network`; catalog never imports it or `OkHttpNetworkClient`. Add `implementation(project(":data:network"))` to **`:app` only** for this real composition; do not add a consumed catalog-to-network implementation edge. Existing `core:common` supplies the coordinator. Root reconciles the actual K3 consumed assembly with registry policy under its ownership; the full map already permits app-to-network, so this does not introduce a new conceptual DAG edge. Provider needs only Android framework APIs; no AndroidX FileProvider dependency. Root edits module/manifest/DI files; workers must receive disjoint ownership.

Honest guarantee: the factory makes an authorizer argument mandatory and owns the only engine initialization; Kotlin's function type cannot prove an arbitrary builder installs or invokes that authorizer. The security guarantee therefore also requires review/testing of this sole root-owned builder and the existing `OkHttpNetworkClient.awaitResponse` physical-enqueue path. Keep the builder local to AppGraph, unavailable through UI/navigation/ShellPorts/service getters; do not retain/publish the returned generic transport or permit a second builder/ungated acquisition route. Search all production factory/network construction call sites during review. Unit fixtures may supply controlled builders in tests; production app callers use the single reviewed expression above. Do not claim type-level enforcement that arbitrary callback code cannot provide.

`AppGraph` retains one facade alongside its single open database and shared settings/coordinator. Do not create a second catalog/acquisition graph in a Worker/JobService. Call recovery once before exposing transfer/import execution; propagate recovery failure, preserve old active lookup availability. `ports()` currently creates only tiny catalog/rules adapters, so downloads/bulk bindings must be explicitly added when their real shell consumers exist; do not register a partial aggregate `CatalogRepository`.

Trusted validator and endpoint resolver live privately in the Android factory/profile code. They admit only the reviewed exact source/version/query policy, finite enforced limits, legal framing, intent/scope/language and redirect origins. Arbitrary caller labels, host suffixes and restored consent are insufficient. Keep English API pagination as the default; mixed bulk/foreign printing approval remains exactly as recorded. ## Provider decision: custom same-UID completed-only mapping

The actual single durable directory contains partials `p-{hash}-a{attempt}`, prepared candidates `p-{hash}-a{attempt}-verified`, completed files at that same candidate name, and sync sentinels. Filename prefix/suffix is **not** evidence of DB completion. Mapping that directory with plain FileProvider XML exposes partials/prepared candidates; a static XML path cannot distinguish their state.

Choose a small custom read-only `ContentProvider` in `feature:catalog`, registered in the app manifest at `${applicationId}.acquisition.artifact`, `exported=false`, `grantUriPermissions=false`, no secondary process. This manifest flag is valid for a custom provider; the review's `grantUriPermissions=true` rule applies to AndroidX FileProvider specifically. No filesystem XML mappings, intent grant flags, sharing actions or `grantUriPermission` calls.

Use a private process registry populated **only inside** the verified `withArtifactFile` callback. The registry holds the exact validated file/descriptor and active lease, keyed by an opaque canonical URI such as `/completed/{actual-opaque-artifact-basename}`. Build this URI with Android `Uri.Builder`, using the registered authority and the actual callback file identity; never fabricate a plausible string for an unverified job. URI alone is not proof and registry entries are never created from caller URIs.

`openFile` verifies same UID (`Binder.getCallingUid() == Process.myUid()`), exact authority/path, no query/fragment/user-info or encoded traversal, read mode exactly `"r"`, and an active registry lease for that exact URI. It opens only the registered canonical regular file using a read-only `ParcelFileDescriptor`; no caller path resolution or database/coroutine work in provider callbacks. `openAssetFile` delegates to that same check and returns whole-file `AssetFileDescriptor(pfd, 0, -1)`; `openTypedAssetFile` admits only this same whole-file read route (no conversion). CancellationSignal overloads check the signal before opening and use the same validation. Write/insert/update/delete/batch/call entrypoints reject. Query/type expose only minimal metadata for the same admitted entry and reject all other paths. Same-UID calls outside a pin fail closed; shell/other-app calls fail even if they know a URI. A provider created before `Application.onCreate` safely sees an empty registry and needs no graph initialization.

This intentionally restricts resolver access to an active trusted pin. `catalogSource` uses `withArtifactFile` to construct the source and perform a real `ContentResolver.openFileDescriptor(uri, "r", cancellationSignal)` read/close before returning metadata. The local `contentUri` belongs to `CatalogBulkImportSource`; it is not a field of `VerifiedArtifact`. The descriptor's provenance carries the separate upstream requested/final URIs. The local URI may subsequently be unavailable until the trusted importer rebinds it; installed generations never need to reopen it. Durable completed artifact/job status remains available independently of this transient provider registration. On process recreation the registry starts empty and is repopulated only after durable validation. This restricted availability is a concrete design tradeoff for root's independent review, not an assertion that an arbitrary completed URI remains freely reopenable.

If root requires general completed-URI reopening outside these trusted callbacks, choose a different reviewed design: a durable completed-only directory plus explicit completion publication/recovery and FileProvider, or a custom provider that pins across FD lifetime. Those entail new durability/lifetime work. Do not silently broaden the registry provider to synchronous DB lookup/runBlocking or map the existing mixed directory.

## Binding and descriptor lifetime

Inside `withPinnedInput`, require artifact source kind and a descriptor, then call `withArtifactFile(descriptor.jobId, cancel)`. Compare the entire durable descriptor with the supplied descriptor; build the canonical URI from that callback's actual file and require exact source URI equality. Read `engine.status` **inside the pin**, require the same COMPLETED descriptor and nonnull `consentId`, and derive/compare the remaining source metadata from the durable request/artifact. Never trust caller consent ID/display metadata or select the first matching settings consent.

Register the provider lease; any genuine resolver descriptor used for binding/readback is held in a lexical `.use` inside this action and closed before invoking/returning from its owning scope. Call `consume(suppliedVerifiedFlow, durableConsentId)` directly and return its result. Keep the provider lease and file pin until `consume` finishes membership resolution, activation and acknowledgement reconciliation. Finally close all adapter-owned resolver descriptors, unregister the lease, then let the file guard release. Do not return flows, files, PFDs or registry leases to UI; public factory methods return only existing typed ports/source metadata. Provider opens are a locator/readback surface, not the bulk import byte authority.

The registry must serialize open-versus-unregister and retain provider-created descriptors so cancellation cleanup closes every adapter-owned outstanding descriptor before releasing the pin. Use `ParcelFileDescriptor.AutoCloseInputStream(pfd).use` for resolver reads; this closes both stream and resolver wrapper. Close retained raw PFDs idempotently at lease exit, with no close-listener thread or asynchronous pin. No sleeps, detached FD scopes, background pipe copying, or hardlinks. Native verification must establish actual same-process resolver PFD close behavior; duplicated/escaped descriptors are prohibited internal misuse, and closing one PFD cannot revoke arbitrary duplicated Linux FDs. Keep all production call sites lexical. If cross-process or independently owned resolver consumers are later required, this design needs a new lifetime review.

Cancellation while waiting for a pin must use the existing token-aware guard; cancellation inside the callback closes resolver reads and verified stream, unregisters and propagates `CancellationException`. Do not swallow cancellation as an ordinary outcome. Removal waits for the existing whole-import pin, then durably unlinks through the engine. Process death drops FDs/registry/locks; DB/file recovery remains engine-owned. A prepared rename has no registry entry until reconciliation commits COMPLETED. Hash mismatch/symlink/missing file rejects without publication. Installed content survives later artifact removal because data/source proof reside in the installed generation.

Task4 still needs the separately reviewed removal/install fence and immutable installed consent provenance. A file pin alone does not prove that a revoked-consent writer cannot activate while a removal request is pending. Persist the exact completed consent ID delivered to `consume`, revalidate/fence relevant installs before removal acknowledgement, preserve selected imports/new consents/user data, and acknowledge only after durable scoped removal. Do not hold the consent gate for an entire import.

## Android execution lifetime

Add actual `INTERNET` and `ACCESS_NETWORK_STATE` manifest permissions under root ownership. The required `connection` adapter uses `ConnectivityManager`/validated network capabilities (including actual WiFi transport), never a fixed success result. Run artifact hashing/fsync/import on caller-owned IO execution. Check actual available space before writes; finite size projections need measured reserve for artifacts, staging DB/WAL and old active generation. Available-space admission does not replace ENOSPC handling.

UI starts/resumes only after explicit exact-intent approval and queues durable work. Worker/JobService obtains the same facade from the application graph and calls `runner.run(jobId, workerCancellationToken)` in its structured execution scope. OS stop/cancellation cancels and joins; application initialization does recovery without automatically resuming transfers. Waiting network/WiFi/consent states remain durable/visible and need explicit scheduler requeue policy, not an in-engine detached loop.

API34+ qualifying user-initiated transfer scheduling and reviewed WorkManager fallback are additional Task3 platform adapters, not implemented by this factory proposal. Root must select/pin scheduler dependency/permissions, network constraints, notification/foreground requirements and retry policy against actual target APIs before implementation. Force-stop prevents scheduled execution until the OS/user permits restart; durable rows are recovery evidence, not proof that jobs continue through force-stop.
