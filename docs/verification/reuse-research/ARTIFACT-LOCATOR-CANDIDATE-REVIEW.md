## Blocking finding

**The final owned/caller PFD loses close-on-exec on API23.** AcquisitionArtifactProvider.kt:156 calls `ParcelFileDescriptor.dup(temporary)` after opening the temporary FD with O_CLOEXEC. In pinned android-6.0.1_r81 ParcelFileDescriptor.java, static dup delegates to `Os.dup(orig)`. Actual libcore_io_Posix.cpp `Posix_dup` calls `dup(oldFd)`, whose new descriptor has FD_CLOEXEC cleared. Closing the temporary descriptor therefore leaves the tracked and returned descriptor without the required close-on-exec protection. This matters to this packet's private lexical-handle boundary: an exec can inherit the actual readable artifact handle even though the original atomic open requested O_CLOEXEC.

The correction must preserve close-on-exec on the actual owned/returned descriptor and add a meaningful native flag assertion. **Do not use the initial suggested Os.fcntlInt/F_SETFD correction on min23**: further source review found fcntlInt marked @hide in API23; official current Android documentation identifies it as added in API30. F_GETFD via that API is likewise unsuitable for an unguarded API23 fixture. Public API23 OsConstants also lacks F_DUPFD_CLOEXEC. Pinned Linux headers define that command as 1030, but a numeric command cannot make hidden fcntlInt public.

Root must settle a legitimate API23 ownership-transfer/duplication solution before correction. A small reviewed native duplication/query adapter can atomically duplicate with F_DUPFD_CLOEXEC and return an integer for public PFD.adoptFd, without hidden FileDescriptor.getInt APIs. This review does not authorize broad native/config work or weaken the accepted flag requirement. A returned-resolver-FD native F_GETFD assertion should accompany the approved implementation. Existing fixtures cannot detect the flag loss. PFD.open and a Parcel roundtrip also use plain open/dup in pinned API23 Parcel JNI, so neither is a source-backed CLOEXEC fallback.

### Requested public fcntlLong/fcntlVoid follow-up

Exact API23 android.system.Os has only fcntlFlock/fcntlInt/fcntlVoid, all marked @hide. **fcntlLong does not exist** there, in libcore.io.Os, or in libcore.io.Posix. Posix JNI has fcntlInt (native fcntl(fd,cmd,arg)) and fcntlVoid (fcntl(fd,cmd)); no fcntlLong registration or implementation. Consequently neither a long overload nor a void overload supplies a public min23 solution. Fresh exact hashes: android.system.Os `de87987ed94739df2d835e6c8eac01fa94d7e3cad5d15f7313f35e9b25f422c6`; libcore.io.Os `dd76487bd2334c84d95faa87053a0a0ab6c31cbf08602b5f912f23ef94e189da`; Posix.java `d54acd5eacc839af387e581d4f47df0467628aa35295de99693d220dc8662ea3`.

This is confirmed ABI provenance, not a guessed literal, and it still cannot make a hidden API public.
