# code-engine

## Summary
Read-only code audit of the acquisition engine and network contract at pkt@315747d. No network was used and nothing was written. File basenames used in evidence map to these paths under pkt/android-app: AcquisitionContracts.kt, InfrastructureContracts.kt and Values.kt are in core/model/src/main/kotlin/.../core/model/. LocalAcquisition.kt, EnglishSearchPageCodec.kt, AcquisitionPayloadCodec.kt, DurableArtifactFiles.kt and AndroidArtifactFiles.kt are in feature/catalog/src/main/kotlin/.../feature/catalog/. OkHttpNetworkClient.kt and WireDispatchGuard.kt are in data/network/src/main/kotlin/.../data/network/. The test files LocalAcquisitionTest.kt and OkHttpNetworkClientTest.kt are in the matching src/test trees. AppGraph.kt is at app/src/main/kotlin/.../di/AppGraph.kt.

Headline findings:
(1) There is no production wiring at all. Nothing constructs LocalAcquisition or OkHttpNetworkClient, and nothing implements validateTrustedRequest, endpointFor or connection. :app does not depend on :data:network. No project manifest declares INTERNET. authorizeWireDispatch is internal, and the transport's default WireDispatchGuard lets every request through. The only validators are test lambdas, which accept everything or match a single request exactly.
(2) Every RequestSpec field is an engine constant. timeout is fixed at 120 s, and OkHttp treats it as the overall deadline for the whole response, body included. charge is NONCHARGED, retry classification is NEVER_AUTOMATIC with maxAttempts==1, there is no idempotency key, and maxResponseBytes equals the reservation. Accept is always application/json and User-Agent is always the constructor default. Profiles cannot change either.
(3) OkHttp turns any non-2xx response (including 429) into Failure(TRANSPORT) with no metadata, so the engine's RateLimited/waitRateLimit path is dead code in production. A 429, 5xx, timeout or IOException while the device is connected ends the job FAILED. A user resume of a FAILED job always restarts it from scratch (attempt+1, at most 3 attempts per job). transferred_bytes is never reset by a restart.
(4) Budget: each search page reserves maxPageBytes, and each remote response reserves A = min(maxArtifactBytes, Known size), even when resuming with Range. Successful responses are settled to actual bytes. Every response that does not complete stays charged at the full reservation.
(5) Language rules: the engine constrains ENGLISH_CARDS only for EnglishSearch. A RemoteFile labelled ENGLISH_CARDS (for example default_cards) passes engine validation with any kind or language. The catalog importer's VERIFIED_ARTIFACT check also accepts it.
(6) Consent is an exact DownloadIntent equality that includes resource, expectedBytes, checksum and version. Dated file URLs therefore need fresh approval on every refresh.
(7) Profile gaps: no metadata-then-file or HTML link-discovery step, no per-profile Accept, timeout or headers, no decoded-size bound for gzip RemoteFile, no Content-Type or framing check, no free-space preflight, no conditional refresh. Range resume across a cross-origin redirect is impossible because Range is stripped. A remote response must finish within 120 s, including an fsync and a DB transaction per chunk.

## Discrepancies
- LocalAcquisition.kt:273/:307-312/:396/:406/:787-792 implement 429 handling (RateLimited → waitRateLimit with at least 30 s, up to 24 h). OkHttpNetworkClient.kt:184-192/:239 never delivers 429 metadata: every non-2xx becomes Outcome.Failure(TRANSPORT) (the header comment at :28 says 'Non-2xx responses are failures'). The engine's 429 path is dead code with the production transport, and the comment at :308-309 ('a user/scheduler retry waits') does not describe what actually happens.
- LocalAcquisition.kt:416-417 and :458 say production network wiring invokes authorizeWireDispatch for every physical enqueue. No such wiring exists. OkHttpNetworkClient's default WireDispatchGuard (:40) calls enqueue() unconditionally, and authorizeWireDispatch is internal, so data:network or app cannot call it.
- LocalAcquisition.kt:25 says 'Required adapters must enforce reviewed provider/source profiles'. No production validateTrustedRequest or endpointFor exists, and the test lambdas accept everything (LocalAcquisitionTest.kt:80-82).
- The name AcquisitionLimits.maxDecodedBytes suggests a decompression bound, but the engine applies it only to EnglishSearch JSONL output (LocalAcquisition.kt:356/:360). It is never applied to RemoteFile GZIP.
- EndpointProfile.retry.initialDelay, maximumDelay and (mostly) honorRetryAfter are part of the contract but inert for acquisition, because the engine mandates maxAttempts==1 and NEVER_AUTOMATIC (LocalAcquisition.kt:431/:468/:470).
- For a redirect hop the engine calls endpointFor(request, actualUri) (LocalAcquisition.kt:429) but uses only that profile's origin, secret and retry. OkHttp keeps using the initial spec.endpoint's requestsPerSecond and allowedRedirectOrigins for every hop (OkHttpNetworkClient.kt:145/:177). Per-hop profiles look authoritative but are only partly applied.
- AcquisitionLanguageScope.ENGLISH_CARDS is enforced strictly only for EnglishSearch (LocalAcquisition.kt:753). A RemoteFile tagged ENGLISH_CARDS is unconstrained, and FullCatalogContracts.kt:60 accepts any ENGLISH_CARDS artifact from provider scryfall. This conflicts with the stated policy that strict English cards come only via EnglishSearch INITIAL_URI and never via default_cards.
- provenance.retrievalStartedAt keeps the first attempt's start across restarts (LocalAcquisition.kt:176, restart at :235-239 does not clear started_*), so for a restarted job it is not the start of the successful retrieval.
- The comment at LocalAcquisition.kt:258 ('A ranged request may legally receive a full 200 representation') explains why a Range resume reserves the full allowance. The engine still never accepts that 200: it discards it as RestartResponse (:274) and keeps the charge.
