## Discrepancies
- Rate figures differ across official pages. /docs/api/rate-limits says /cards/search is 2/second (500 ms), while the FAQ blocked page says 'We ask that you keep your API traffic to under 10 requests per second.' The stricter per-endpoint 2/s figure is the operative one. The repo uses 600 ms; the task's etiquette uses >=1 s.
- Docs say the Accept header may be generic. The code sends Accept: application/json, which is fine. Docs prefer UA like 'MTGExampleApp/1.0'. The repo draft proposes 'CommandLibrary/<actual app version>', which is consistent.
- EnglishSearchPageCodec accepts the real next_page, but the codec test (EnglishSearchPageCodecTest.kt:21) and LocalAcquisitionTest.kt:108 construct next_page differently from the live server (alphabetized parameters with format=json in the middle). No fixture matches the real string.
- The List docs mark warnings Nullable, but the codec (EnglishSearchPageCodec.kt:50) would reject an explicit "warnings": null. The live response omits the key, so there is no failure today.
- ENGLISH-PROFILE-DRAFT records page 1 at 860,496 bytes on 2026-10-12. Today's probe measured 860,498 bytes, a 2-byte drift with an identical total_cards of 116,009.
- Docs steer large-data users to bulk files ('you must use the bulk data files' for rapid lookups; the FAQ says consider bulk instead of 'constantly requesting live data'). The CARDS profile pages 663 search requests because no English-only bulk file exists. This is allowed but is the less-preferred path. Default Cards is not English-only (it includes the printed language when a card exists in one language only).
- Edge cache TTL on search pages is 16 h (max-age=57600). Scryfall's advice to cache downloaded data is 'at least 24 hours', and bulk files refresh every 12-24 h. A fresh traversal on the same day may replay cached pages.
- The repo ENGLISH-PROFILE-DRAFT says the profile's 600 ms is stricter than the upstream 500 ms. This is confirmed by the rate-limits page.
