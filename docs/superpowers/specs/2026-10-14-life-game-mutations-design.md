## Boundary and APIs

Build concrete storage mechanics around a trusted synchronous local engine callback, not a substitute semantic game engine. Callback executes after loading checked authoritative state inside one Database transaction; it must not perform database operations, external durable effects, publication or suspend work. Aborted/crashed attempts may invoke it again, so no exactly-once callback claim. Actual reducer/timing/random/undo selection correctness and process recovery are separate reviewed prerequisites before GameService binding.

Proposed concrete public helper signatures (visibility allows storage integration tests; not new core contracts):
- LifeActionWrite(archive: GameEventArchive, checkpoint: GameCheckpoint).
- SqlLifeGameMutator(Database,LifePayloadCodecPort).action(id: GameId, expected: Revision, expectedSequence: Long, build: (StoredLifeGame, Long) -> Outcome<LifeActionWrite>, cancel: CancelToken): Outcome<StoredLifeGame>. Callback receives checked current record and allocated event ID.
- checkpoint(id, expected, expectedSequence, updatedAt: UtcTimestamp, build: (StoredLifeGame) -> Outcome<GameCheckpoint>, cancel): Outcome<StoredLifeGame>.
- markDelivered(id: GameId, occurrenceId: EntityId, channels: Int, cancel): Outcome<Unit>. Bits visual1/haptic2/audio4; nonempty subset1..7, OR-only idempotent operational bookkeeping. No OS effect or exactly-once delivery claim.

Extract internal transaction-local read methods from SqlLifeGameStore/SqlLifeEventReader without changing public read/create behavior. Never nest Database transactions. Writer loads checked current core/seat/graph and operational projections before callback, checks expected revision AND sequence (STALE_REVISION for either mismatch); missing record remains NOT_FOUND. Guard counter overflow before callback. Existing strict metadata/payload limits and cancellation propagate. Caller-returned contradictory packet is INVALID_INPUT; already stored contradiction CORRUPT_DATA; incomplete legacy operational Knowledge is UNSUPPORTED rather than guessed.

## Operational result and alert reconciliation

Result identity is stable once first recorded, including reopen/undo/refinish; never remove result row or insert a second identity. New/changed result has revision=new game revision; first/nonretracted confirmation has exactly one coherent outcome per roster seat. A first-ever result must be nonretracted; an already stored retracted result may remain unchanged. Retraction preserves original result facts (winners/outcomes/time/reason), changes retracted and revision; reopening reason lives in event. Refinalizing may update facts under same result identity. Known->Absent/Unknown is invalid. Existing unchanged result keeps its existing revision; graph ensures completion/retraction compatibility. No automatic loss inference from legacy partial outcomes; live conversion must be explicit later.

Old current alerts cannot disappear; identity/game/target/firedAt immutable, old acknowledgments cannot be removed or rewritten; null->timestamp permitted without UTC ordering. Fired-ID history cannot shrink. New occurrences get deliverymask0; existing masks retained; acknowledgment changes update same row atomically. Undo builder must carry operational acknowledgment/occurrences forward, not copy old provenance blindly. Extra old ledger rows remain untouched. markDelivered validates existing checked occurrence then ORs requested bits without modifying snapshot/revision/sequence; it cannot change ack/target/fired metadata. Separate delivery side effect may still duplicate after crash; no exactly-once OS guarantee.

## System checkpoint

Does not append event or advance revision; sequence advances exactly once via same CAS. Preserve creation, lastEvent, lastSettled, result, roster/counters/settings/designations/turn identity/activity and every other non-timing field. Only clock settlement/pause/anchor/fired IDs, elapsed settlement/anchor/pause, appended alert occurrences and recoveredProcessSessionId may change. Clock mode/bank IDs/initial balances/owner/policies immutable here; countdown may pause at zero, never switch owner/refill. A paused countdown cannot be started or charged by settlement; only the previously running active seat bank/shared bank may decrease, inactive seat balances remain exact. A paused elapsed timer cannot be started or charged by settlement; running elapsed game/turn totals cannot decrease, and turn lineage stays exact. Recovery may pause/reanchor but never refunds/reassigns totals. This narrow settlement relation applies BOTH current-checkpoint vs immutable last afterAction and archive.before vs loaded current, as well as new system checkpoints. Same operational alert carry-forward rules. Current sequence plus recovered session/settled event identifies the current system checkpoint; no fabricated user event or claim of a historical checkpoint audit table (schema has none). Actual monotonic process-session settlement/recovery engine still required before use.
