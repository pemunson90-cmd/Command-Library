## Blocking findings

1. **Canonical face data cannot preserve multiple printings' face images.** `CatalogContracts.kt:30` puts `CardFace.image` inside canonical `CardRecord.faces`; `PrintingRecord` at line62 has only one top-level `imageUri`. The foundation design requires equal repeated canonical payloads and one canonical face row. Two printings of the same multiface oracle can therefore conflict solely through different face images, or lose the association between a printing and its own front/back assets. Provide typed printing-face assets keyed by printing and face position/identity, retain original image references, and define canonical equality to exclude printing-specific fields. Reflect that relationship in the physical schema. Do not resolve this by dropping supplied assets, accepting an arbitrary first printing's values, or weakening equality of actual canonical rules data. Required regression: two distinct printings of one multiface oracle retain their distinct assets and produce one canonical card, while a genuine canonical-field conflict still fails.

2. **Unresolved face relationships lose source identity.** `FaceRelationship` at `CatalogContracts.kt:24` carries only `relatedOracle` and `relatedFace`. A relationship supplied as a foreign printing/raw producer ID cannot be represented while its Oracle mapping is unknown. Add typed source-qualified related-printing/raw identity independently from optional resolved Oracle/face identity; preserve supplied relationship kind/order and unresolved state. A prose evidence string or URI must not substitute for the foreign ID. Required regression: a meld/related-part target supplied only by raw printing ID round-trips without guessing an Oracle ID, name match or language transfer.

3. **Storage row bounds contradict maximum-page continuation.** `InfrastructureContracts.kt:72` restricts `SqlRequest.maxRows` to100, while the accepted lookup design fetches `limit + 1` and permits a100-item public page. The required101st row cannot be requested through this storage contract. Retain the100-item public page bound and give storage explicit bounded headroom, or review a concrete alternative continuation query with equivalent snapshot semantics. Required regression: maximum public page can detect a real next row; the extra row never leaks into the public page.

4. **Typed transaction errors need explicit rollback semantics.** At `InfrastructureContracts.kt:103–109`, transaction operations return `Outcome`, while `Database.transaction` accepts a callback returning arbitrary `T`. A callback can return normally after an operation reports failure or validation rejects staged writes; ordinary exception-based transaction handling would then commit those writes. Preserve the historical aggregate signature, but define the transaction contract explicitly: failed transaction operations mark rollback-only; a domain validation rejection has a typed abort mechanism; the transaction cannot report success or commit after either. Exceptions/cancellation roll back before propagation/classification. Cancellation after durable commit remains committed and is reconciled through persisted status. Add meaningful adapter tests for write-then-operation-failure, write-then-domain-abort, and cancellation around commit. A helper that merely computes the next revision is not evidence for any database transaction guarantee.

These findings were sent to the orchestrator before completing this draft. Only the orchestrator/assigned author should implement corrections; this reviewer changed no production source.

## Accepted structure and declaration coverage

Every component group has its expected public port(s), preserving the historical synchronous/suspend/Flow distinctions: core; network; storage; vault; settings; catalog; rules; search; decks; collection; pricing; validation; brackets; recommendations; transfer; life; inference; AI; links; shell. The six `CatalogRepository` methods remain declared. Public DTOs are meaningful snapshots covering the required fields and additional parity entities, with the specific catalog corrections above. No raw-map, platform-handle, `Any` DTO substitute, fake future adapter or unfinished method implementation was found. `Any?` occurs only in equality overrides.

The local segregation is sound and should be retained:

```kotlin
suspend fun CatalogLookup.lookupName(input: String, page: PageRequest, cancel: CancelToken): Outcome<Page<CardRecord>>
suspend fun CatalogStatus.status(cancel: CancelToken): Outcome<LocalCatalogStatus>
suspend fun CatalogImport.`import`(source: CatalogImportSource, chunks: Flow<ByteChunk>, onProgress: (JobProgress) -> Unit, cancel: CancelToken): Outcome<CatalogImportResult>
```

These summarize actual members, not proposed extension implementations. The importer consumes caller-owned streaming bytes without an Android file handle. Status represents persisted generations, dates and installed languages separately from Full/English defaults. Consumers must receive only these implemented capabilities; the aggregate remains unregistered until every method works. Settings read/update/approve can be implemented as actual persistence without starting jobs; if a complete aggregate cannot fulfill its patch semantics, review a concrete segregated interface before wiring it.

`Knowledge` separates known/absent/unknown; `Outcome` separates success/unavailable/failure/unknown. Provenance separates source/version/date, fetched/effective time and generation. Producer-qualified IDs and unresolved foreign identity are represented. Exact BigDecimal amounts retain native units/scale/precision, including TIX. SnapshotList and SnapshotBytes defensively copy collection/byte inputs; the concrete nested DTOs use immutable values. Revision helpers reject stale edits/exhaustion, and cancellation classification explicitly rethrows CancellationException. The inspected tests address these value/helper properties; they do not prove durable adapters, byte framing, serialization, or thread/process behavior.

## Implementation obligations retained

The foundation architecture is otherwise suitable for implementation after the blocking corrections and successful corrected-source hosted compile. Preserve staging/active/retired generations, one canonical FTS row per Oracle/language, separate printing/face relations, persistent pointer activation, old committed data on failure, and non-destructive schema upgrades. Room3-generated schema and bundled FTS5 bound MATCH require actual packaged evidence; a design table is not a generated schema.

Enforce all import limits in the real reader: English only,8MiB input,10000 printing objects,128KiB record,128-row staging batches and nesting32. `CatalogImportLimits` currently declares the first four but not nesting; centralize the fixed nesting ceiling and reject before recursive growth. Validate UTF-8/framing, exact incoming-byte SHA-256, required identity and numeric/relationship fields, duplicate printing IDs, supplied counts and canonical equality. Unknown source dates remain unknown. Ensure stream completion/truncation, byte offsets and final chunks cannot produce partial success. Import mutex acquisition precedes staging mutation; abandoned staging cleanup cannot delete active/retired or user data.

Document and test literal FTS token/phrase/prefix rules, Unicode/punctuation/quotes/keywords, bound parameters, deterministic ordering and generation-pinned cursors. Put an explicit size limit on cursor decoding and choose a typed stale-generation outcome; no mixed-generation page or silent cursor restart. The current unbounded cursor string in PageRequest does not by itself enforce this adapter boundary.

DataStore changes compare revision inside the atomic update, increment once per committed change and persist consents with settings. Approval records express intent but launch no job. `ConsentRecord.permits` evaluates a snapshot only: future transfer adapters must revalidate current persisted revocation, never treat an old copied record as enduring permission. Restore cannot reinstate effective acquisition permission. Failure or cancellation before commit must retain prior settings; consent and revision require close/reopen tests.
