## Blocking corrections

### S1: A successful save can produce a store that cannot reopen (high)

`SettingsStoreFormat.kt:87-100` declares a 16 MiB maximum but `encode` grows an unrestricted `ByteArrayOutputStream`. `SettingsStoreSerializer.kt:15-23` limits only reading. Public model strings and lists are not size limited. For example, a `SettingChange.Budget(Knowledge.Unknown(reason, ...))` with a 16 MiB nonblank ASCII reason passes `validate`, writes more than 16 MiB including the envelope, and can return Success. The current DataStore instance retains it in memory; reopening fails as CORRUPT_DATA. Repeated consent approvals can reach the same condition without any single oversized field. The old valid snapshot has already been replaced.

Reject an oversized encoded candidate before committing any store replacement, with a bounded encoder/preflight so the protection does not itself allocate arbitrarily large output. Return a truthful typed mutation failure and preserve the old bytes/revision. Apply the same bound to updates and approvals, including envelope/CRC bytes. Add regression coverage around the exact size boundary and a public-operation rejection followed by reopening and checking the prior snapshot. None of the 35 submitted tests covers this path. This finding is established by source flow, not an executed reproduction in this review.

### S2: UTF-8 conversion silently changes persisted values and consent scope (high)

`SettingsStoreFormat.kt:281-284` uses `String.toByteArray(UTF_8)` and `:324-329` uses `String(raw, UTF_8)`. Both replace malformed input rather than reject it. A valid-checksum payload containing malformed UTF-8 in a permissive string field is accepted with replacement characters, then a later ordinary update overwrites it with different bytes. Conversely, an accepted input containing an isolated UTF-16 surrogate, such as a resource URI ending in `\uD800`, is encoded with replacement and returns in-memory Success; after restart the URI is different and a consent may match the replacement URI rather than the exact originally approved intent. The core `ResourceUri` and identity wrappers only require nonblank strings, so they do not prevent this.

Use strict UTF-8 encoder and decoder behavior (`CodingErrorAction.REPORT`, or equivalent) for all stored strings. Invalid persisted encoding must be CORRUPT_DATA with no overwrite; non-encodable mutation input must fail without changing bytes or revision. Test invalid/truncated UTF-8 with a recomputed valid CRC, isolated input surrogates, normal supplementary Unicode round trips, and exact consent intent equality across reopen. The current tests cover lengths/checksums/enums but not encoding validity. This is source-established; no new JVM test was executed here.

### S3: Correct the claimed absence of product defaults (documentation/scope)

The task card and handoff call cache zero / `retainRulings=false` choices without a documented product source. SPEC A05 and K01 explicitly require default online-on-view art with a bounded cache; A03 requires Lean to retain fetched rulings, and A04 retains full offline rules. The task-authorized K2 state has no acquisition/cache/rulings consumer, so zero image cache and no requests are a defensible temporary foundation state, not evidence that these product requirements were removed or unspecified. Budget Unknown and Wi-Fi-only do not conflict with the inspected requirements; Full/English matches D-14.

Correct the handoff and active integration notes to identify the temporary K2 adaptation and retain explicit obligations before relevant consumers are wired: preserve fetched rulings and existing user choices, provide the required art default, and define a versioned/default-state transition rather than interpreting a persisted K2 zero as the user's opt-out. Do not expose Lean/cache/delete-download success controls while the affected behavior is absent. No new product approval is needed merely to preserve the already required scope.

## Findings without a demonstrated implementation blocker

- **Revision and atomicity:** all three `SettingsRepository` methods are implemented. Update checks the expected revision inside `updateData`; revision, timestamp and consent state share one serialized value. Ordered patches abort on rejection. Equality/no-op rule is documented and tested, including stale no-ops; exhaustion is typed. Approve increments once only when a new effective consent is created. Tests cover concurrent same-revision writers and concurrent approvals. No empty future method or pretend download executor was found.
- **Cancellation:** core `cancellableOutcome` checks structured coroutine cancellation and the token, rethrowing cancellation; update/approve check inside the transaction. The closed-store conversion only converts repository-scope cancellation when the caller/token remains active. Submitted tests exercise token checkpoints and cancellation while the transform is held. A cancellation after the commit may throw with committed state retained, as documented; no rollback claim is made. This review has not re-proven DataStore's process-death guarantees.
- **Corruption/newer schema:** explicit magic/schema/CRC, length/count/tag/domain checks, no replacement corruption handler, and cause-chain classification preserve unreadable stores. Newer schema receives a typed failure with version evidence; no settings reset path exists. Tests check unchanged bytes after failures/reopen. S2 is the gap in the current corruption claim. The CRC is accidental-corruption detection, not authentication against a party able to rewrite app-private files.
- **Exact values:** decimal unscaled integer, scale and unit are persisted without floating point; timestamps retain nanoseconds; consent stores all intent fields. Provider, resource, version, language, pack, checksum and expected-byte knowledge participate in exact intent equality through the accepted core `permits`. The adapter neither canonicalizes nor redirects a resource, so textual differences cannot broaden permission. It is not a URL/origin/redirect validator; future acquisition must use its reviewed canonical source/redirect guard and must not infer permission from a similar URL or provider alone.
- **Installation binding:** the Context factory puts the UUID in `noBackupFilesDir`, while settings remain under filesDir. On a new repository, missing/invalid UUID produces a new ID, making old consents inert without erasing settings or fabricating revocation. I/O failure is typed. The original-ID-return test explicitly demonstrates that records are preserved and can become effective again with that ID. This is binding to an installation, not cryptographic anti-replay. A future in-app restore onto the same installation must invalidate/omit restored acquisition consent or rotate an appropriate consent epoch; replaying an old settings file under the unchanged ID can otherwise resurrect a revoked record. This absent future restore operation is not claimed implemented or accepted here.
- **Bounded auxiliary input:** `InstallationIdStore.kt:39` reads the entire UUID file with `readText`. Consider limiting this to a small UUID-sized input (oversized means invalid) so a damaged private file cannot cause an unbounded allocation. Unlike the settings payload it is not accepted from restore/import in the current design; this is defensive hardening, not a third demonstrated consent bypass.
- **Resource lifecycle:** installation output uses `use`, sync and a cleaned-up temporary file; serializer streams remain owned by DataStore; in-memory streams own no OS resource. The repository offers `close` and joins its scope, with tests for reopening. Production must use one live repository per store/process; this implementation does not claim multiprocess support.
- **Stage-limited fields:** source notices are always empty and downloaded-data removal is ignored because neither source-notice integration nor downloaded data exists here. The handoff discloses both. Treat these as explicit K2 limitations, not K02 attribution or data-deletion acceptance. Before real data/download consumers exist, implement truthful removal/notice semantics or review capability segregation; do not wire unsupported product controls to this aggregate.

## API 23 and remaining acceptance evidence

`SystemSources.kt:14` calls `Math.floorDiv(long,long)` and `Math.floorMod(long,long)`, platform APIs added in API 24. The module declares minSdk 23. The current source/configuration contains no explicit core-library-desugaring setup, and submitted tests inject a fake clock. This is a concrete compatibility exposure requiring evidence, not proof of an inevitable runtime crash: the selected D8 may backport these calls as part of ordinary desugaring. Either use an API-23-safe quotient/remainder implementation with negative-epoch boundary tests, or demonstrate the actual final dex backport and API 23 runtime behavior. Do not add `NewApi` suppressions, a fake clock in production, or silently raise minSdk to bypass this check.

Run `:feature:settings:lintDebug` with NewApi fatal, alongside the regression tests and assembleDebug, before closing scoped compatibility review. The accepted tuple review already requested this; existing JVM success is not a substitute. This review environment has no `/opt/android-sdk` and only JDK 21, so these Gradle/Android checks were not rerun here. No dependency version probes or network research were performed.

Later K2/runtime evidence remains required: actual Context factory on Android, API 23 read/update/approve/reopen using the system clock, concurrent/cancel behavior under the Android runtime, installation-ID loss with preferences retained, backup/device-transfer excluding the ID, safe atomic replacement/process-death scenarios, and composition-root singleton lifetime.
