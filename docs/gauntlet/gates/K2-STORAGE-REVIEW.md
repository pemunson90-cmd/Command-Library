## Initial findings (retained for traceability)

**S1 — parameter scanner can silently leave a native parameter unbound.** `NamedParameters.kt:39–46` accepts a suffix that is neither a Kotlin letter/digit nor `$`, even when SQLite includes that suffix in its parameter token. Example: `SELECT :a😀 AS first_value, :a AS second_value` with only supplied `a`. The scanner sees one distinct name `a`; SQLite sees two distinct names, `:a😀` and `:a`. `StorageDatabase.kt:199–210` binds only index1 and never compares the native parameter count, so index2 remains NULL. Combining marks such as U+0301 have the same issue. Enforce the promised ASCII-token grammar against SQLite token boundaries and verify native parameter count before stepping; retain first-appearance indexing. Add actual bundled-SQLite regressions, not only scanner-output tests.

Supplementary reproduction used the workspace Python SQLite `3.53.1`, which accepts the two names distinctly. This is evidence of the parser disagreement, not a claimed test of Android's pinned bundled SQLite `3.50.1`. Bundled runtime verification remains required.

**S2 — later writes can escape an engine-aborted transaction.** `StorageDatabase.kt:147–161` executes subsequent statements even after the latch has become rollback-only. A valid `INSERT OR ROLLBACK` can hit a uniqueness constraint and end SQLite's transaction immediately. The adapter returns/latches Failure, but an ignored failure followed by another execute can then write in autocommit mode. The final Room rollback cannot undo that later write. The scanner only rejects control words at the start, so `INSERT OR ROLLBACK` is admitted. Supplementary native SQLite reproduction: BEGIN; insert primary key; duplicate INSERT OR ROLLBACK fails and clears `in_transaction`; insert another row; final ROLLBACK reports no active transaction, and the later row survives. Refuse further query/execute SQL after the first latched non-success and preserve that status; consider rejecting engine-rollback conflict clauses as defense in depth. Add an actual bundled/Room regression with an ignored engine rollback followed by a further write and verify zero surviving rows after reopen. This also protects against SQLite errors that automatically roll back a transaction without explicit conflict syntax.

**S3 — query permits writes with result columns on a writer connection.** `StorageDatabase.kt:176–195` checks column names/count but never requires a read-only prepared statement. `DbTransaction.query` supplies a writer connection, so e.g. `INSERT INTO catalog_name_fts(...) VALUES (...) RETURNING name` is accepted as a query and changes data. A `WITH ... INSERT ... RETURNING` form has the same issue. Acquiring a reader for the top-level path is insufficient to enforce query semantics on the transaction path. Enforce native statement read-only status (or an equivalently complete supported-query policy) before stepping, and add a transaction query regression proving DML RETURNING fails/latches rollback without mutation. Keep normal SELECT/WITH reads and bound FTS reads working.

**S4 — the callback confinement check does not cover abort or latch mutation.** `StorageDatabase.kt:163–173` checks the owner Job only in query/execute's `activeConnection`; synchronous `abort` only checks a non-null unsynchronized connection. An escaped reference on another coroutine/thread can therefore call abort while the callback is active. Moreover, query/execute observe their failure outside the owner check, allowing rejected foreign-coroutine calls to mutate the same non-thread-safe latch. `finish`, `abort`, latch observation and the commit-permission read have no shared synchronization. A foreign abort can race the final permission check, and concurrent observations can lose first-status ordering. Either consistently reject all out-of-scope operations before shared-state mutation, or make scope revocation/latching/commit decision atomic under a documented confinement mechanism. Add cross-coroutine/cross-thread abort and post-callback-use tests; the existing escape test covers only a query after completion. The documented requirement that callers finish operations before `StorageDatabase.close()` is reasonable and should remain explicit; its AtomicBoolean makes repeated close idempotent, not a promise of arbitrary concurrent close safety.
