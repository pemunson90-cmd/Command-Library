### F5. Streaming JSON import per stack

**Codex review correction, 2026-10-11:** R-02 preserves a same-day Scryfall feed observation of gzipped JSONL, not a root array. For that feed, every stack must stream compressed bytes through incremental gzip decompression and bounded newline framing, decode one JSON object per record, then insert bounded batches. Track bytes while framing, impose a stated maximum record size, and abort the staged generation on oversized/malformed records; never silently truncate or load the whole decompressed file. Kotlin/JVM can use incremental buffered byte reads plus per-record kotlinx serialization; Dart can use chunked gzip/UTF-8 conversion plus a bounded record framer and per-record jsonDecode; .NET uses bounded incremental framing plus per-record System.Text.Json; RN runs the same framing in its native import adapter; Rust uses bounded BufRead/framing plus per-record serde_json. Exact framing implementation, limits, Unicode chunk handling, corruption/cancellation and memory remain later acceptance work.

The table below describes candidate parsers for producers that actually send root arrays or other JSON documents, such as verified MTGJSON/Spellbook exports. ARRAY_WRAPPED and root-array visitors are not selected for the preserved Scryfall JSONL contract. Select the producer-specific parser from verified metadata and a validated sample. Evidence: R-02 F1/F2, source https://api.scryfall.com/bulk-data (prior same-day observation, not remeasured); https://jsonlines.org/ and https://dart.dev/learn/tutorial/data-and-json (accessed 2026-10-11).

### F7. Atomic data refresh patterns

- SQLite transactions commit atomically; WAL allows readers and a writer concurrently, but there is only one writer and readers see transaction snapshots. WAL adds companion files that belong to the database state. Sources: https://www.sqlite.org/atomiccommit.html and https://www.sqlite.org/wal.html and https://www.sqlite.org/isolation.html (accessed 2026-10-11).
- Proposal A, preferred for downloaded catalog: build a new generation database in a different path using bounded import transactions, create indexes, validate foreign keys and integrity, close/checkpoint it, then activate that generation under an application lock. Keep user decks/collection in a separate persistent database and preserve stable Oracle/printing IDs across catalog generations. This is an application design recommendation, not an SQLite-provided atomic-file-swap API. Sources for required DB-file precautions: https://www.sqlite.org/wal.html and https://www.sqlite.org/howtocorrupt.html (accessed 2026-10-11).
- Do not rename/delete an open SQLite database or drop its WAL as an assumed safe swap. Proposed robust activation uses immutable generation filenames and a small recoverable active-generation manifest; resolve crash recovery before implementation. UNVERIFIED: durable manifest/rename semantics on the actual Android filesystem and Windows package path; no crash tests performed. Sources: https://www.sqlite.org/howtocorrupt.html and https://www.sqlite.org/wal.html (accessed 2026-10-11).
- Proposal B: stage new rows in the same file, then change the active-generation pointer in one short transaction, retaining old rows until readers finish. Incremental row replacement plus FTS updates can also use a single transaction. Batching live mutations into separate commits does not make the whole refresh atomic; readers would see partial updates unless a generation scheme hides them. This is a design inference from transaction isolation. Source: https://www.sqlite.org/isolation.html (accessed 2026-10-11).
- Cross-file ATTACH transactions in WAL are atomic within each database, not across the complete set. Avoid promising atomic user-data/catalog writes spanning separate WAL files. New catalog IDs may temporarily be absent; preserve user references and resolve them after activation. Source: https://www.sqlite.org/wal.html (accessed 2026-10-11).

Recommend S1 with stable Room 3.0.3 and AndroidX BundledSQLiteDriver as the fallback-compatible path, subject to pinned target smoke builds.
