# R-12 Secure key storage per platform

Path: `docs/gauntlet/research/R-12-key-storage.md`. Every claim carries its source URL and access date. Anything not confirmed by a source is marked UNVERIFIED. Access date for every source below is 2026-10-11 (from `date -u +%F`) unless stated otherwise. Task card: `coordination/tasks/cc-research-12.md`.

## Question

How should Command Library encrypt user API keys at rest on Android and Windows, and which libraries do that in each candidate stack (S1 KMP + Compose Multiplatform, S2 Flutter, S3 .NET MAUI, S4 Avalonia, S5 React Native + RN Windows, S6 Tauri 2)? Feeds GAUNTLET.md 2.H (API keys encrypted at rest with the platform keystore, never logged, never exported in plain text), 2.I (full app backup is a single file, keys excluded by default), and the R-01 secure storage criterion.

## Findings

Conventions: "primary" means vendor or project documentation, package registry metadata, or source code. "Secondary" means a third-party write-up. Page text was read by direct fetch or by streaming `curl | sed | grep`; nothing was saved to disk. Sizes and versions were measured with `curl -sI` and by streaming registry JSON or XML through `jq` or `grep`.

### F1. Android platform

F1.1 Android Keystore protects key material from extraction, not from use.
- "The Android Keystore system lets you store cryptographic keys in a container to make them more difficult to extract from the device." "Key material never enters the application process." "If the app's process is compromised, the attacker might be able to use the app's keys but can't extract their key material (for example, to be used outside of the Android device)." "If the Android OS is compromised or an attacker can read the device's internal storage, the attacker might be able to use any app's Android Keystore keys on the Android device, but it can't extract them from the device." Source (primary): https://developer.android.com/privacy-and-security/keystore (accessed 2026-10-11)
- Hardware backing is conditional: "This feature is enabled only if the device's secure hardware supports the particular combination of key algorithm, block modes, padding schemes, and digests the key is authorized to be used with." Check at runtime with `KeyInfo` (`KeyProperties.SecurityLevelEnum.TRUSTED_ENVIRONMENT` or `STRONGBOX` means secure hardware, for apps targeting API 29+). Same source.

F1.2 StrongBox is optional, slower, and not needed for this use.
- "StrongBox is appropriate for applications requiring the highest level of security, particularly those at risk of physical tampering or side-channel attacks. However, it is slower, more resource-constrained, and supports fewer concurrent operations. For most apps, StrongBox is not necessary." AES 128/256 and HMAC-SHA256 are supported in StrongBox. Request it with `KeyGenParameterSpec.Builder.setIsStrongBoxBacked(true)`; the framework throws `StrongBoxUnavailableException` if unsupported, and the documented remedy is to generate the key without StrongBox. Source (primary): https://developer.android.com/privacy-and-security/keystore (accessed 2026-10-11)
- `setIsStrongBoxBacked` and `FEATURE_STRONGBOX_KEYSTORE` were "Added in API level 28". Sources (primary): https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder and https://developer.android.com/reference/android/content/pm/PackageManager (accessed 2026-10-11)
- `KeyGenParameterSpec.Builder.setKeySize` is "Added in API level 23", consistent with AES-GCM Keystore keys being usable from API 23. Source (primary): https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder (accessed 2026-10-11)

F1.3 Authorizations are fixed at key creation and enforced by the Keystore.
- "Once a key is generated or imported, its authorizations can't be changed." User-authentication binding exists (`setUserAuthenticationParameters`, `BiometricPrompt`), and "If a key only supports biometric credentials, the key is invalidated by default whenever new biometric enrollments are added." Source (primary): https://developer.android.com/privacy-and-security/keystore (accessed 2026-10-11). Consequence for this app: an auth-bound key would lock the user out of their API keys on biometric changes and would force a prompt on every AI call. A key that is not auth-bound is the practical choice (see F5).

F1.4 Keys are scoped to the creating app and cleared by the system on uninstall (inference), and update survival is undocumented.
- Keystore access "is normally limited to the app or system component that created the key", with the caller's UID included "to disambiguate keys from different apps". The `clear_ns` permission is "used as a maintenance operation when apps are uninstalled." Source (primary): https://source.android.com/docs/security/features/keystore (accessed 2026-10-11). No page says in plain words that uninstall deletes the app's keys; that is an inference from `clear_ns`. UNVERIFIED as a plain statement. Tried: developer.android.com keystore page, source.android.com keystore page, the Auto Backup, backup overview, and backup best-practices pages.
- Updates: no source I read states that keys survive an update of the same package signed by the same key. UNVERIFIED as a documented guarantee. Jetpack Security, Tink and the MAUI and Flutter plugins all assume keys persist for the app's installed lifetime. GAUNTLET.md section 3 plans one permanent release key, so release updates keep the same signature. A debug build signed with a different key cannot update a release install in place; Pat would have to uninstall, and the keys would be lost (re-entry needed).

F1.5 Keystore keys do not travel with backups, so restored ciphertext is undecryptable.
- Google's own `EncryptedSharedPreferences` reference: "WARNING: The preference file should not be backed up with Auto Backup. When restoring the file it is likely the key used to encrypt it will no longer be present. You should exclude all EncryptedSharedPreferences from backup using backup rules." Source (primary): https://developer.android.com/reference/androidx/security/crypto/EncryptedSharedPreferences (accessed 2026-10-11)
- Tink's source says that when a keyset cannot be decrypted because the master key is missing, "This is an irrecoverable error. You'd have to delete the keyset in Shared Preferences and all existing data encrypted with it." Source (primary, source code): https://raw.githubusercontent.com/tink-crypto/tink-java/main/src/main/java/com/google/crypto/tink/integration/android/AndroidKeysetManager.java (accessed 2026-10-11)
- Real-world evidence of the failure mode: .NET MAUI issue #18230 (SecureStorage `AEADBadTagException` after Android backup then uninstall and reinstall; "Secure storage calls, including key removal, failed until app storage was cleared"; closed 2024-08-30 by PR #23850) and issue #22239 (`AEADBadTagException` on MAUI 8.0.20, closed 2024-07-19 by a bot for lack of author response). Sources (primary, issue trackers): https://github.com/dotnet/maui/issues/18230 and https://github.com/dotnet/maui/issues/22239 (accessed 2026-10-11)
- Consequence: the ciphertext file must live in a location excluded from both cloud backup and device-to-device transfer (F6), and the app must treat "ciphertext present but Keystore key missing or decryption fails" as "no key stored" (delete the ciphertext, ask the user to re-enter) rather than crash.

F1.6 Auto Backup facts relevant to exclusion.
- Default backed up: shared preferences, files from `getFilesDir()`, database files from `getDatabasePath`, external files dir. "Auto Backup excludes files in directories returned by `getCacheDir()`, `getCodeCacheDir()`, and `getNoBackupFilesDir()`." Limit: "Every app can allocate up to 25 MB of backup data per app user." and "If the amount of data is over 25 MB, the system calls `onQuotaExceeded()` and doesn't back up data to the cloud." Source (primary): https://developer.android.com/identity/data/autobackup (accessed 2026-10-11). Cross-cutting note for the architect: the full card database (GAUNTLET.md 2.A) will exceed 25 MB, so it must live outside the backed-up domains or cloud backup of everything else silently stops.
- Android Keystore is not mentioned at all on the Auto Backup page. Its own guidance for credentials is Block Store (F1.9).

F1.7 Jetpack Security (`androidx.security:security-crypto`) is deprecated; do not adopt.
- Release notes, 1.1.0-beta01 (June 4, 2025): "Deprecated all APIs in favour of existing platform APIs and direct use of Android Keystore." The latest version on Google Maven is 1.1.0 (the release page dates it July 30, 2025). Sources (primary): https://developer.android.com/jetpack/androidx/releases/security and https://dl.google.com/android/maven2/androidx/security/security-crypto/maven-metadata.xml (version list ends at 1.1.0) (accessed 2026-10-11)
- Cryptography guide: "All APIs in the security-crypto Jetpack library were deprecated in the stable release of version 1.1.0. There won't be any subsequent releases of this library." Source (primary): https://developer.android.com/privacy-and-security/cryptography (accessed 2026-10-11)
- API reference: `EncryptedSharedPreferences` "Deprecated in 1.1.0 ... This class is deprecated. Use android.content.SharedPreferences instead."; `EncryptedFile` "Use java.io.File instead."; `MasterKey` points to `javax.crypto`. Sources (primary): https://developer.android.com/reference/androidx/security/crypto/EncryptedSharedPreferences and https://developer.android.com/reference/androidx/security/crypto/package-summary (accessed 2026-10-11)
- Google's current recommendation is therefore "direct use of Android Keystore" plus the algorithm guidance: "If your app requires greater key security, use the Android Keystore system", and prefer AES with 256-bit keys in GCM mode. Source (primary): https://developer.android.com/privacy-and-security/cryptography (accessed 2026-10-11). I found no official step-by-step replacement guide. The DataStore plus Tink pairing in blogs is community consensus (secondary): https://proandroiddev.com/goodbye-encryptedsharedpreferences-a-2026-migration-guide-4b819b4a537a and https://blog.kinto-technologies.com/posts/2025-06-16-encrypted-shared-preferences-migration (accessed 2026-10-11). Treat it as UNVERIFIED as an official Google recommendation.

F1.8 Tink on Android.
- `tink-android` 1.23.0 is the latest on Maven Central (metadata `lastUpdated` 2026-07-09); the POM carries the Apache License 2.0 header; the jar is 3,320,451 bytes (measured with `curl -sI`). Sources (primary): https://repo1.maven.org/maven2/com/google/crypto/tink/tink-android/maven-metadata.xml and https://repo1.maven.org/maven2/com/google/crypto/tink/tink-android/1.23.0/tink-android-1.23.0.pom (accessed 2026-10-11)
- Tink ships a thin class `AndroidKeystore` (Android M, API 23 or newer): `generateNewAes256GcmKey(alias)`, `getAead(alias)`, `deleteKey`, `hasKey`; it generates an AES-256-GCM key in the `AndroidKeyStore` provider. It warns the Keystore "can only handle a limited number of requests in parallel" and that on `BadPaddingException` "the ciphertext is not decryptable and retrying will not help". Source (primary, source code): https://raw.githubusercontent.com/tink-crypto/tink-java/main/src/main/java/com/google/crypto/tink/integration/android/AndroidKeystore.java (accessed 2026-10-11)
- Tink's older `AndroidKeysetManager` now says: "We don't recommend using this class. Instead, directly use AndroidKeystore." and "because Android Keystore is unreliable, we strongly recommend disabling it by not setting any master key URI", adding that Tink "runs a self-test to detect such problems and disables Android Keystore accordingly". Source (primary, source code): https://raw.githubusercontent.com/tink-crypto/tink-java/main/src/main/java/com/google/crypto/tink/integration/android/AndroidKeysetManager.java (accessed 2026-10-11). This is Google's Tink team saying Keystore reliability varies by device, so the design must tolerate Keystore failure (F1.5 handling, plus a first-use self-test).
- Tink repo license: Apache-2.0. Source (primary): https://github.com/tink-crypto/tink-java (accessed 2026-10-11)

F1.9 Block Store is not suitable for this requirement.
- "Block Store allows developers to save and restore up to 16 byte arrays", "maximum 4kb per entry", persists across uninstall/reinstall "If the user enables Backup services", and needs Google Play services; end-to-end encryption needs API 29 and a screen lock. Source (primary): https://developer.android.com/identity/block-store (accessed 2026-10-11). Using it would copy API keys into Google's backup infrastructure, which conflicts with GAUNTLET.md 2.H ("never exported") and 2.I ("keys excluded"). Not recommended.

### F2. Windows platform

F2.1 DPAPI (`CryptProtectData`, user scope) is the baseline primitive.
- "Typically, only a user with the same logon credential as the user who encrypted the data can decrypt the data. In addition, the encryption and decryption usually must be done on the same computer." "However, a user with a roaming profile can decrypt the data from another computer on the network." With `CRYPTPROTECT_LOCAL_MACHINE`, "any user on the computer on which CryptProtectData is called can use CryptUnprotectData to decrypt the data" (so never set that flag). Optional entropy is "a password or other additional entropy". The function adds a MAC "to guard against data tampering". Library `Crypt32.dll`; minimum client Windows XP. Source (primary): https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata (accessed 2026-10-11)
- The prompt-struct flow is deprecated: "The prompt-based flow controlled by this parameter is deprecated and will be removed in February 2027." Pass `NULL` for `pPromptStruct`. Same source.
- Microsoft's current guidance ranks the options: "Use the Windows Credential Manager. Call CredWrite and CredRead ... which encrypts them with the user's logon session key." then "Use DPAPI for local secret storage. Call CryptProtectData to encrypt secrets that must be persisted locally." It also says "Never log passwords or secrets." and "When you have finished using passwords or secrets in memory, immediately overwrite the buffer by calling SecureZeroMemory." Source (primary): https://learn.microsoft.com/en-us/windows/win32/secbp/handling-passwords (page dated 2026-07-16; accessed 2026-10-11)
- DPAPI stores nothing: "DPAPI merely applies cryptographic protection to the data. It does not store any of the protected data; therefore applications calling DPAPI must implement their own storage of the protected data." Source (primary, archived 2001 article, XP era; algorithms described there are historic): https://learn.microsoft.com/en-us/previous-versions/ms995355(v=msdn.10) (accessed 2026-10-11)
- Same article, on the limit that matters here: "A small drawback to using the logon password is that all applications running under the same user can access any protected data that they know about." Optional "secondary entropy" "does increase the difficulty of one application, running under the same user, to compromise another application's encryption key", but if entropy "is simply saved to a file unprotected, then adversaries could access the entropy". Same source.
- The same article lists non-technical failure modes: "The Password Reset Disk can be stolen", and DPAPI "is also susceptible, as any password-based system is, to social engineering attacks". It describes domain-controller backup keys and the Password Reset Disk as the recovery paths, and says that when a user changes their password "all MasterKeys are re-encrypted under the new password." Whether an administrator-forced password reset on a standalone machine orphans protected data is UNVERIFIED in this pass; the app must treat a failed unprotect as "key lost, ask again" regardless. Same source.
- The API page states no per-call size limit. UNVERIFIED for any maximum; API keys are well under 1 KB so it does not matter here.
- The API page states no packaging prerequisite (it lists "desktop apps | UWP apps"). That DPAPI works from an unpackaged jpackage-style JVM app is shown in practice by KSafe's Windows vault (F3.1) but is not stated by Microsoft; UNVERIFIED as an explicit Microsoft statement.

F2.2 Credential Manager (`CredWrite`/`CredRead`, generic credential).
- `CredentialBlobSize` "cannot be larger than CRED_MAX_CREDENTIAL_BLOB_SIZE (5*512) bytes", which is 2,560 bytes. Generic target name up to 32,767 characters. `CRED_TYPE_GENERIC`: "The credential will not be used by any particular authentication package. The credential will be stored securely but has no other significant characteristics." Persistence: `CRED_PERSIST_LOCAL_MACHINE` is "visible to other logon sessions of this same user on this same computer and not visible to logon sessions for this user on other computers"; `CRED_PERSIST_ENTERPRISE` is also visible "to logon sessions for this user on other computers" (it can roam), so use `LOCAL_MACHINE`. Minimum client: "Windows XP [desktop apps only]". Source (primary): https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw (accessed 2026-10-11)
- The page defines no per-app access control for generic credentials. That any process of the same user can read them is the java-keyring author's claim (secondary, F3.1 and F5), not a Microsoft statement. UNVERIFIED from Microsoft docs.

F2.3 WinRT `PasswordVault` (Credential Locker).
- "Lockers are specific to a user. Apps running in an AppContainer (for example, UWP apps) can only access the contents of their own locker (for the current user). Apps not running in an AppContainer (for example, regular Desktop apps) can access all the user's lockers, including those of AppContainer apps." Introduced in Windows 10 build 10240. Source (primary): https://learn.microsoft.com/en-us/uwp/api/windows.security.credentials.passwordvault (accessed 2026-10-11)
- The guide describes roaming: "securely store and retrieve user credentials, and roam them between devices with the user's Microsoft account", "you can only store up to 20 credentials per app", usable "in WinUI as well as other desktop apps, such as WPF and WinForms", and "Only use the credential locker for passwords and not for larger data blobs." Source (primary): https://learn.microsoft.com/en-us/windows/apps/develop/security/credential-locker (accessed 2026-10-11)
- Whether roaming actually occurs on current Windows 11 builds: UNVERIFIED (docs claim it; I found no current test). If it does roam, API keys would be copied to the user's other devices, which conflicts with "never exported". That alone argues against `PasswordVault` for API keys. I did not search for a JVM binding to this WinRT API (UNVERIFIED whether one exists), and it would need a WinRT projection that DPAPI and Credential Manager do not.

F2.4 JNA gives a JVM app direct access to DPAPI.
- `com.sun.jna.platform.win32.Crypt32Util` exposes `cryptProtectData(byte[] data)`, `cryptProtectData(byte[] data, int flags)` and an overload taking entropy, flags and description (flags example in its javadoc: "CRYPTPROTECT_LOCAL_MACHINE | CRYPTPROTECT_UI_FORBIDDEN"). Source (primary, source code): https://raw.githubusercontent.com/java-native-access/jna/master/contrib/platform/src/com/sun/jna/platform/win32/Crypt32Util.java (accessed 2026-10-11)
- `jna-platform` latest is 5.19.1 (Maven metadata `lastUpdated` 2026-06-12); `jna-platform-5.19.1.jar` is 1,416,385 bytes and `jna-5.19.1.jar` is 1,950,853 bytes (measured with `curl -sI`). License header: "SPDX-License-Identifier: Apache-2.0 OR LGPL-2.1-or-later". Sources (primary): https://repo1.maven.org/maven2/net/java/dev/jna/jna-platform/maven-metadata.xml and https://raw.githubusercontent.com/java-native-access/jna/master/LICENSE (accessed 2026-10-11)
- On `master`, JNA's `Advapi32.java` contains no `CredRead`/`CredWrite` text (match count 0) and `Wincred.java` returned no matches, so Credential Manager from a JVM needs a library such as java-keyring (F3.1) or hand-written JNA structures. UNVERIFIED for any other branch or release. Method: streamed the raw files through grep.

F2.5 Compose Desktop packaging is unpackaged by default, and jlink can trim needed modules.
- `TargetFormat` in the Compose Multiplatform Gradle plugin lists `AppImage, Deb, Rpm, Dmg, Pkg, Exe, Msi`; there is no MSIX target. Source (primary, source code): https://raw.githubusercontent.com/JetBrains/compose-multiplatform/master/gradle-plugins/compose/src/main/kotlin/org/jetbrains/compose/desktop/application/dsl/TargetFormat.kt (accessed 2026-10-11). Consequence: an S1 Windows build installs as MSI or EXE without MSIX package identity, so nothing extra isolates its secrets from other processes of the same user (consistent with F5).
- KSafe's docs state Compose Desktop release builds "use jlink to bundle a trimmed JRE" and that JNA needs `sun.misc.Unsafe` from `jdk.unsupported`, so `modules("jdk.unsupported")` must be added to `nativeDistributions` or the OS vault is silently replaced by a key file beside the data. Source (primary for KSafe's behavior; secondary for whether JNA itself needs the module): https://raw.githubusercontent.com/ioannisa/KSafe/main/docs/JVM_PROTECTION.md (accessed 2026-10-11). Whether a hand-written JNA `Crypt32Util` call fails or works without the module in a trimmed runtime is UNVERIFIED (not tested here). The remedy is a CI smoke test of the packaged Windows build (Recommendation and Risks).

F2.6 Packaged (MSIX) versus unpackaged, summary for the three APIs.
- DPAPI: no packaging requirement stated on the API page (F2.1). Credential Manager `CREDENTIAL`: "Windows XP [desktop apps only]" (F2.2); behavior inside a full-trust MSIX app is not stated, UNVERIFIED. `PasswordVault`: usable from "WinUI as well as other desktop apps" (F2.3); an AppContainer app sees only its own locker, a non-AppContainer desktop app "can access all the user's lockers", so an MSIX app only gets isolation if it runs in an AppContainer (inference from the quoted sentences; full-trust MSIX behavior UNVERIFIED).
- The java-keyring author claims packaged-with-identity MSIX apps get protection from other same-user processes and unpackaged jpackage apps do not (secondary, F3.1). Microsoft docs I read do not confirm it, so UNVERIFIED. Compose Desktop cannot produce MSIX natively (F2.5) in any case.
- For a JVM app: DPAPI through JNA works unpackaged (KSafe in practice, F3.1), Credential Manager through java-keyring (JNA underneath), `PasswordVault` has no binding I found.
- Folder semantics for the ciphertext file: Windows known folders include `FOLDERID_LocalAppData` ("Local", `%LOCALAPPDATA%`) and `FOLDERID_RoamingAppData` ("Roaming", `%APPDATA%`). Source: https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid (accessed 2026-10-11). The page text I captured gave names and paths only, not the roaming semantics sentence, so the statement that Local does not roam is by the folder's name and common practice; UNVERIFIED as a quoted Microsoft sentence. DPAPI's own roaming-profile remark (F2.1) is why the ciphertext should go in the Local folder.

### F3. Libraries per candidate stack

Scoring scale used below for the R-01 secure storage criterion: 0 (no workable path) to 5 (turnkey on both platforms with mature, maintained code). Scores are my judgement from the cited facts.

### F5. Threat model

Plain statement first. None of the approaches in this document protect against: (1) malware or any other process running as the same Windows user, (2) a rooted or otherwise compromised Android OS using the app's Keystore keys on the device, (3) a thief who has the unlocked phone or an unlocked Windows session, (4) the key being visible in process memory while the app is making a request, (5) the user pasting the key somewhere else (clipboard, screenshots) or the provider logging it, (6) a malicious or compromised AI provider endpoint, and (7) a LAN endpoint reached over plain `http`, where the key crosses the network in clear text. Items 6 and 7 are my reasoning, not sourced findings.

| Threat | Android design (Keystore AES-GCM key, ciphertext in no-backup dir) | Windows design (DPAPI user scope, ciphertext in LocalAppData) |
|---|---|---|
| Other apps on the device or machine | Protected by the app sandbox and by Keystore UID scoping (F1.4). | Not protected from other processes of the same user (F2.1: "all applications running under the same user can access any protected data that they know about"). Protected from other Windows users. |
| Device backup extraction (cloud backup, device-to-device, `adb backup`) | Protected if the file is excluded (F6); even if copied, ciphertext is useless without the non-extractable key (F1.1, F1.5). Android 12 also changed `adb backup`: "app data is excluded from any other system data that is exported from the device" for apps targeting API 31+ (https://developer.android.com/about/versions/12/behavior-changes-12, accessed 2026-10-11). | A copied file or profile backup is useless on another account or machine (F2.1, KSafe note in F3.1). A backup that includes both the user's DPAPI master key material and the file, plus the password, is not protected (archived article, F2.1). |
| Stolen locked device, disk imaging | Protected: key material stays in secure hardware (F1.1). | Protected by the user's logon credential; weaker if the logon password is weak (archived article: all DPAPI protection "rests on the password provided"). |
| Stolen unlocked device or session | Not protected. A key that is not auth-bound can be used by anyone using the unlocked phone. Binding to biometrics would block this but breaks on enrollment changes and prompts on every AI call (F1.3). | Not protected. |
| Malware as the same user (Windows) | n/a | Not protected. java-keyring's README: "credentials can be read by any app you run even if not elevated" (secondary). Optional entropy only raises the bar slightly (F2.1). |
| Rooted or compromised Android OS | Keys cannot be extracted but can be used on the device (F1.1). | n/a |
| Debugger or memory read of the running app | Not protected: the plaintext key exists in memory during use. JVM strings cannot be reliably zeroed (my reasoning); use byte or char arrays where the HTTP client allows. | Same. Microsoft advises `SecureZeroMemory` for native code (F2.1); no JVM equivalent. |
| Roaming or sync to other devices | Excluded by backup rules (F6); Block Store not used (F1.9). | Use `%LOCALAPPDATA%`, not Roaming, for the ciphertext file (F2.6); DPAPI blobs are decryptable on other machines only for roaming-profile users (F2.1). `CRED_PERSIST_ENTERPRISE` and `PasswordVault` can roam, so avoid both (F2.2, F2.3). |
| Keys in logs | Not covered by storage encryption; needs explicit redaction. | Same. |

Never-logged mechanics (GAUNTLET.md 2.H). OkHttp's logging interceptor: "The logs generated by this interceptor when using the HEADERS or BODY levels have the potential to leak sensitive information such as "Authorization" or "Cookie" headers"; use `redactHeader()`. Source: https://raw.githubusercontent.com/square/okhttp/master/okhttp-logging-interceptor/README.md (accessed 2026-10-11). Ktor's client Logging plugin has `sanitizeHeader { header -> header == HttpHeaders.Authorization }`. Source: https://ktor.io/docs/client-logging.html (accessed 2026-10-11). Provider auth headers differ (Authorization bearer, `x-api-key`, and others); the full header list per provider belongs to the AI-provider research and is UNVERIFIED here. Whether any provider accepts the key as a URL query parameter (which would end up in access logs and crash reports) is UNVERIFIED. The safe rule is: send keys only in headers, wrap the key in a type whose `toString()` is redacted, and never put it in analytics or crash payloads.

Clipboard. Android: sensitive copied data "should be flagged with ClipDescription.EXTRA_IS_SENSITIVE or android.content.extra.IS_SENSITIVE before calling ClipboardManager.setPrimaryClip()" (relevant only if the app ever copies a key out, which it should not; pasting a key in is the user's action). Source: https://developer.android.com/privacy-and-security/risks/secure-clipboard-handling (accessed 2026-10-11).

### F6. Excluding keys from backups

F6.1 Android Auto Backup and device-to-device transfer.
- Rules files: Android 12 and higher uses `android:dataExtractionRules` with `<cloud-backup>`, `<device-transfer>` (and `<cross-platform-transfer>`) sections; Android 11 and lower uses `android:fullBackupContent`. "Even if your app targets Android 12 or higher, you must also specify another set of XML backup rules to support devices that run Android 11 (API level 30) or lower." "If there are no rules for a particular backup mode, such as if the <device-transfer> section is missing, that mode is fully enabled for all content except for no-backup and cache directories." `<exclude>` takes precedence over `<include>`; no wildcards. Source (primary): https://developer.android.com/identity/data/autobackup (accessed 2026-10-11)
- Domains: `file` is "directories returned by getFilesDir()", `database` is "directories returned by getDatabasePath()", and `root` is the file system where all private files of the app are stored. Same source.
- `android:allowBackup="false"` is not sufficient for transfers: "On devices from some device manufacturers, specifying android:allowBackup="false" disables cloud-based backup and restore (such as Google Drive backups) but doesn't disable device-to-device transfers for the app." Same source. Google's backup guide adds: "If the <device-transfer> attribute is not set, all the application data will be transferred during a D2D migration." Source (primary): https://developer.android.com/privacy-and-security/risks/backup-best-practices (accessed 2026-10-11)
- Google recommends the standard backup system with exclusions over a custom export: "If your backup includes particularly sensitive data, then we recommend to either exclude this data or, if you cannot exclude it, require end-to-end encryption". It also warns that custom "export" or "backup" capabilities "that creates a copy of the app data in directories readable by other apps" are "hence prone to being leaked" (relevant to the single-file backup in GAUNTLET.md 2.I; the user chooses the destination through the system file picker). Same backup-best-practices page.
- Layers to apply together: (a) put the key ciphertext file in `noBackupFilesDir` (excluded from Auto Backup by default); (b) also add explicit rules so a later refactor cannot silently re-include it; (c) never store keys in Room, DataStore in `filesDir`, or shared preferences.

Concrete rules (my construction from the documented syntax). The exact backup-domain path that maps to `noBackupFilesDir` is not stated on the pages I read (UNVERIFIED), which is why layer (a) is the primary control. The XML below guards a `secrets/` directory under `getFilesDir()` in case a file ever lands there, and excludes the card database domain so the 25 MB quota (F1.6) is not blown:

```xml
<!-- res/xml/data_extraction_rules.xml (Android 12+) -->
<data-extraction-rules>
  <cloud-backup>
    <exclude domain="file" path="secrets/"/>
    <exclude domain="database" path="card_database.db"/>
  </cloud-backup>
  <device-transfer>
    <exclude domain="file" path="secrets/"/>
  </device-transfer>
</data-extraction-rules>
```

```xml
<!-- res/xml/backup_rules.xml (Android 11 and lower) -->
<full-backup-content>
  <exclude domain="file" path="secrets/"/>
  <exclude domain="database" path="card_database.db"/>
</full-backup-content>
```

Manifest: `android:allowBackup="true"` (explicit), `android:dataExtractionRules="@xml/data_extraction_rules"`, `android:fullBackupContent="@xml/backup_rules"`. Whether to leave Auto Backup on at all is an architect and Pat decision; the simplest alternative is `allowBackup="false"` plus the secrets rules above. Syntax source: https://developer.android.com/identity/data/autobackup (accessed 2026-10-11).

F6.2 Per-stack manifest access. Flutter: edit `android/app/src/main/AndroidManifest.xml` (the plugin README shows this exact file). MAUI: `Platforms/Android/Resources/xml/auto_backup_rules.xml` per Microsoft's guide (F3.3). KMP and RN: standard Android manifest. Tauri mobile: generated Android project; how its manifest and `res/xml` are customised is UNVERIFIED (not researched).

F6.3 The app's own backup file (GAUNTLET.md 2.I, 2.H). This is design guidance built from the findings, not a sourced claim:
- Keep secrets out of every store the exporter reads. The key store is a separate component with its own file and its own interface; settings and provider configuration (base URL, model id, a "key present" flag) live elsewhere. The exporter has no dependency on the key store, so keys cannot leak into the file by construction.
- Add a test that seeds a fake key (a unique sentinel string), runs a full export, and asserts the sentinel appears nowhere in the output bytes, including inside compressed entries.
- On import, never overwrite existing keys, and treat the file as containing none. After a restore onto a new device the UI shows each provider as "needs key".
- "Keys excluded by default" (2.I) implies an opt-in to include them. If Pat wants that opt-in, the file must carry them encrypted under a user passphrase, never in plain text (2.H). Building blocks verified: `PBKDF2withHmacSHA256` is available from API 26 on Android (https://developer.android.com/reference/javax/crypto/SecretKeyFactory), and OWASP says "PBKDF2-HMAC-SHA256: 600,000 iterations (recommended)" and prefers Argon2id where available, which needs an extra library (https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) (both accessed 2026-10-11). The app's minSdk is not yet decided (later gate); if it is below 26, PBKDF2-SHA256 needs a library. My recommendation is to omit the opt-in (feature absent from the UI) unless Pat rules otherwise, since a passphrase vault is more attack surface than re-entering a few keys.

## Options

Android (applies to S1 and any stack with native Android code):
- A1. Direct Android Keystore: non-exportable AES-256-GCM key, ciphertext in `noBackupFilesDir`. Small amount of `javax.crypto` code. No new dependency. Matches Google's stated direction (F1.7).
- A2. Same as A1 through Tink's `AndroidKeystore.getAead(alias)`. Cleaner AAD handling, +3.3 MB, Apache-2.0.
- A3. KSafe (or flutter_secure_storage in S2, MAUI SecureStorage in S3): off-the-shelf stores. Differences in F3.
- A4. Jetpack Security `EncryptedSharedPreferences`: deprecated, no further releases. Rejected.
- A5. Block Store / Credential Manager restore keys: sends keys into Google backup. Rejected for 2.H and 2.I.
- A6. StrongBox request with fallback: allowed but Google says it is not necessary for most apps and it is slower. Not recommended for API keys.

Windows:
- W1. DPAPI user scope (no `LOCAL_MACHINE`), ciphertext file in `%LOCALAPPDATA%`, entropy constant. JNA `Crypt32Util` for a JVM app; `ProtectedData` for .NET; `CryptProtectData` directly in Rust or C++.
- W2. Credential Manager generic credential (`LOCAL_MACHINE` persistence), one credential per provider, 2,560-byte cap. Microsoft ranks it first in its current guidance; in JVM it needs java-keyring (last release 2023) or hand-written JNA structs.
- W3. flutter_secure_storage's hybrid (AES-GCM files plus a key in Credential Manager). Works, but AES-128 and ciphertext in the Roaming folder.
- W4. WinRT `PasswordVault`: documented to roam to other devices, 20-credential cap, no JVM binding found. Rejected.
- W5. Per-use passphrase or Windows Hello gating. Not recommended as default: adds friction and protects only against casual use of an unlocked session.

## Recommendation

Android: A1. Generate a non-exportable AES-256-GCM key in `AndroidKeyStore` (not auth-bound, TEE default, no StrongBox request), encrypt each API key with AAD = provider id plus a schema version, store IV and ciphertext in a file under `noBackupFilesDir`. Run a first-use encrypt/decrypt self-test. On any `GeneralSecurityException` or a missing key, delete the ciphertext, mark the provider "needs key", and ask the user to re-enter; never fall back to plaintext. Do not adopt `androidx.security:security-crypto`. Use A2 only if the architect prefers Tink's wrapper. Add both backup XML files from F6 plus the `noBackupFilesDir` placement.

Windows: W1. DPAPI user scope through JNA `Crypt32Util.cryptProtectData` with `CRYPTPROTECT_UI_FORBIDDEN`, a fixed application entropy blob, no `LOCAL_MACHINE`, ciphertext in `%LOCALAPPDATA%\Command Library\`. Add `modules("jdk.unsupported")` (and probe whether more modules are needed) in `nativeDistributions`, and gate release on a CI smoke test on a `windows-latest` runner that round-trips a secret through the packaged distributable. Treat a failed unprotect as "key lost". Use W2 only if Pat wants keys visible in Windows Credential Manager.

## Risks

- Keystore unreliability on some devices (Tink's own warning, F1.8; MAUI field reports, F1.5). Mitigation: self-test, fail closed to "re-enter key", no plaintext fallback.
- Same-user malware on Windows can read the keys (F2.1, F5). Not mitigable by storage choice; say so in the About or security notes. Optional per-session passphrase is possible later.
- jlink-trimmed runtimes may break the JNA/DPAPI path silently or loudly (F2.5). UNVERIFIED for hand-written JNA calls; CI smoke test required.
- Backups: the Android 11-and-lower rules file is easy to forget; `allowBackup="false"` does not stop device-to-device transfer on some devices (F6.1); the card database exceeds the 25 MB Auto Backup quota, which stops cloud backup entirely if left in a backed-up domain (F1.6).
- Keys die with uninstall, factory reset, debug-to-release switch, signing-key change, or changing the package name (F1.4). Expected behavior; the UI needs a clear "re-enter your key" path and the first-run flow should say so.
- Update survival of Keystore keys is undocumented (F1.4). Low risk in practice; test one release-to-release update on a real device at the first milestone.
- Single-maintainer dependencies (KSafe, credential-keychain-kotlin, java-keyring last release 2023). First-party code avoids this; if KSafe is chosen, pin the version and review its Windows vault code.
- A "include keys in backup" opt-in, if requested, adds a passphrase KDF and a format that must never fall back to plain text (F6.3). Recommended to omit.
- Logging leaks (F5): HTTP client logging at header level, crash reporters, and provider URLs with key query parameters (UNVERIFIED per provider). Needs a lint or test that greps logs and request URLs for a sentinel key.
- Dependency pinning: GAUNTLET.md section 3 requires pinned dependencies; versions recorded here (JNA 5.19.1, Tink 1.23.0, KSafe 3.3.0, flutter_secure_storage 11.2.0) are the 2026-10-11 snapshot and must be re-checked when the architect pins them.

## Confidence

High for the Android recommendation: Google's own docs deprecate Jetpack Security and point to direct Keystore use (F1.7), the backup behavior is documented (F1.5, F1.6, F6.1), and Tink's source corroborates the design.

High for DPAPI as the Windows baseline and for the statement of what it does not protect against: Microsoft's API page and its current "Handling Passwords" guidance (F2.1) agree, and the archived article states the same-user limit explicitly.

Medium for the per-stack scores and for the S1 JVM details: they depend on third-party library status that I measured on 2026-10-11 (versions, dates, stars) and on a jlink behavior reported only by KSafe's docs.

Low for these items, all marked UNVERIFIED above: Keystore key survival across app updates and deletion on uninstall as plain statements (F1.4); DPAPI per-call size limit (F2.1); admin password reset effect on DPAPI data (F2.1); whether `PasswordVault` roams today and whether a JVM binding exists (F2.3); full-trust MSIX behavior of Credential Manager and the MSIX isolation claim (F2.6); whether a hand-written JNA call survives a jlink-trimmed Compose runtime (F2.5); the backup-domain path for `noBackupFilesDir` contents (F6.1); the charlesportwoodii Tauri plugin's publication status and the Tauri mobile manifest customisation path (F3.6, F6.2); expo-secure-store Windows support (F3.5); provider-specific header and query-parameter key handling (F5); credential target name collisions in flutter_secure_storage on Windows (F3.2).

Notes against GAUNTLET.md: section 10 states no key-storage facts, so nothing there is contradicted. Section 2.H says keys are "encrypted at rest with the platform keystore (verify per platform at Gate 1)". Verified result: that phrase is accurate for Android (hardware-backed Keystore). Windows has no hardware keystore in these APIs; DPAPI and Credential Manager are software protections tied to the user's logon (F2.1), so the wording should read "OS user-scope encryption" for Windows. Section 2.I says keys are "excluded by default", which implies an opt-in that 2.H forbids doing in plain text; this needs a ruling, or the opt-in simply stays absent (F6.3). Appendix A does not mention key storage beyond the original request for "API keys", so no conflict.
