## Question

How do S1 Compose Multiplatform, S2 Flutter, S3 .NET MAUI, S4 Avalonia, S5 React Native plus React Native Windows, and S6 Tauri 2 support adaptive panes, foldables, desktop interaction, accessibility, and reproducible UI tests?

## Findings

### F1. Size classes and product implications

Android width classes are compact <600dp, medium 600 to <840dp, expanded 840 to <1200dp, large 1200 to <1600dp, and extra-large >=1600dp. Height classes are compact <480dp, medium 480 to <900dp, and expanded >=900dp. Classification uses available app window space, not device identity. `currentWindowAdaptiveInfo(supportLargeAndXLargeWidth = true)` opts into larger widths. A medium-width, compact-height window can be unsuitable for two panes. Source: https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes (accessed 2026-10-11).

Design recommendation: extend GAUNTLET 2.J's three named classes to cover large and extra-large, use logical client dimensions after display scaling and insets, and test just below/at/above every width breakpoint. Do not classify a 1920-pixel monitor as extra-large without checking scaling and actual window width. This corrects the recovered draft's screen-pixel assumption. Basis: F1 source (accessed 2026-10-11).

### F3. S1 fold posture, hinge exclusion, state

Android `WindowInfoTracker` streams `WindowLayoutInfo`; its `displayFeatures` can contain `FoldingFeature`. `FoldingFeature` provides `state`, `orientation`, `bounds`, `isSeparating`, and `occlusionType`. Half-open horizontal corresponds to tabletop; half-open vertical corresponds to book. Compute the hinge within the content coordinate system and place important controls in the available regions. Adaptive helpers expose posture and folding features; pane scaffolds can use hinge-aware directives. Sources: https://developer.android.com/reference/kotlin/androidx/window/layout/FoldingFeature and https://developer.android.com/develop/ui/compose/layouts/adaptive/foldables/make-your-app-fold-aware (accessed 2026-10-11).

The Android fold signal is distinct from common window sizing. UNVERIFIED: Windows posture/hinge equivalent and the value returned by desktop `windowPosture`; the CMP release lists window-core, not proof of an Android WindowInfoTracker equivalent. Source inspected: https://github.com/JetBrains/compose-multiplatform/releases/tag/v1.12.1 (accessed 2026-10-11).

Recommended state ownership: keep selected card/deck, search query, scroll position, unsaved edits, navigation and game state above branches that swap panes. `rememberSaveable` handles supported UI state; ViewModel/SavedStateHandle and durable storage cover recreation and process death as appropriate. Ordinary `remember` alone does not promise restoration. Source: https://developer.android.com/develop/ui/compose/state-saving (accessed 2026-10-11). UNVERIFIED: identical restoration guarantees on desktop without a Windows build and persistence tests.

### F4. S2 adaptive and foldable support

Flutter recommends evaluating current available width with `MediaQuery`/`LayoutBuilder`, not platform/device labels. NavigationBar versus NavigationRail can switch at 600 logical pixels; list-detail/supporting panes can be composed from ordinary layout widgets. Source: https://docs.flutter.dev/ui/adaptive-responsive/general (accessed 2026-10-11). Adopt F1 breakpoints explicitly; do not assume Flutter automatically implements every Material size class.

`MediaQueryData.displayFeatures` and `dart:ui.DisplayFeature` expose bounds, fold/hinge type and posture state. Obstructed hinge area is part of the view coordinate space. Use the bounds plus orientation/state to partition content, including tabletop life counters. Sources: https://api.flutter.dev/flutter/widgets/MediaQueryData/displayFeatures.html and https://api.flutter.dev/flutter/dart-ui/DisplayFeature-class.html (accessed 2026-10-11). UNVERIFIED: physical OEM coverage and completeness of Windows fold signals; no device execution occurred.

`flutter_adaptive_scaffold` was planned for discontinuation by upstream, so it is not a maintenance-safe dependency simply because it provides canonical panes. Source: https://github.com/flutter/flutter/issues/162965 (accessed 2026-10-11). Recommend first-party layout primitives; successor package maturity is UNVERIFIED. Folding/unfolding can lose state when widget structure changes; keep state ownership stable across layout changes. Source: https://docs.flutter.dev/ui/adaptive-responsive/best-practices (accessed 2026-10-11).

## Recommendation

Carry S1 and S2 to the R-01 decision. Keep the Kotlin fallback conditional on a packaged Windows accessibility spike proving Narrator labels, focus, editing, menus, live counter announcements and system text scaling, plus dependency resolution of desktop pane/navigation artifacts. Java Access Bridge/NVDA success alone cannot satisfy GAUNTLET 2.J's explicit Narrator requirement. If S1 cannot pass, S2 is the strongest researched alternative here, with S3 a credible native-Windows option. Basis: F2/F6/F7/F8, sources accessed 2026-10-11.

At Gate 2 define logical size classes, a height override, hinge-safe life counter geometry and state ownership independently of framework. At implementation time verify physical foldable sensors and accessibility against pinned binaries. These are recommendations, not authorization to start app code during Gate 1.

## Risks

1. Windows Narrator parity on S1 is unresolved; do not silently replace the named reader with NVDA. Evidence: F7.
2. Stable framework release names can conceal alpha/RC component dependencies; old RNW docs cannot certify Fabric. Evidence: F2/F5/F6.
3. Flutter adaptive scaffold maintenance and third-party window/drop plugins add dependency selection work. Evidence: F4/F6.
4. Resize/fold can recreate UI branches; no stack automatically guarantees preservation of edits/game state. Ownership and persistence tests are required. Evidence: F3/F4.
5. A synthetic posture or golden screenshot does not validate sensor coverage, UIA or TalkBack. Evidence: F8.
6. Current issue closure/fix versions, exact package pin compatibility, OS scaling behavior and runtime measurements remain UNVERIFIED. The audit found primary descriptions and reports; it did not build or install these stacks.
