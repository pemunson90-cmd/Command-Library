#### F1.1 llama.cpp (ggml)
- License MIT, "Copyright (c) 2023-2026 The ggml authors". Source: https://raw.githubusercontent.com/ggml-org/llama.cpp/master/LICENSE (accessed 2026-10-11)
- UNVERIFIED inherited release assertion: tag b11552, published 2026-10-10; latest status/date and pre-release designation were not rechecked. Prior session described continuous numbered builds rather than semver stable releases. Source: https://github.com/ggml-org/llama.cpp/releases (prior access recorded 2026-10-11, via WebFetch summary)
- Model format: GGUF only. Quantizations "1.5-bit, 2-bit, 3-bit, 4-bit, 5-bit, 6-bit, and 8-bit integer quantization". Source: https://raw.githubusercontent.com/ggml-org/llama.cpp/master/README.md (accessed 2026-10-11)
- Backends table (README): CUDA (Nvidia), HIP (AMD), Hexagon (Snapdragon), OpenCL (Adreno GPU), OpenVINO "[In Progress]" (Intel CPUs, GPUs, NPUs), SYCL (Intel GPU), Vulkan (GPU), WebGPU, plus CPU. Source: same README (accessed 2026-10-11)
- UNVERIFIED inherited asset-size assertions: release assets b11552 relevant here (sizes are whole tool bundles, including llama-server, llama-bench and so on, not the minimal library): Android arm64 CPU `llama-b11552-bin-android-arm64.tar.gz` 71.4 MB; Android arm64 Snapdragon (CPU, Adreno OpenCL, Hexagon NPU) 56.1 MB; Windows x64 CPU zip 18.6 MB; Windows x64 Vulkan 31.9 MB; Windows x64 CUDA 12.4 253 MB plus a 373 MB cudart zip; Windows x64 CUDA 13.4 146 MB plus 404 MB cudart; Windows x64 SYCL 142 MB; Windows x64 ROCm 10.0 246 MB; Windows x64 OpenVINO 85.5 MB; Windows arm64 CPU 11.8 MB; Windows arm64 OpenCL Adreno 12.6 MB; Windows arm64 Vulkan 24.8 MB; Windows arm64 CUDA 13.4 139 MB. Source: https://github.com/ggml-org/llama.cpp/releases/expanded_assets/b11552 (accessed 2026-10-11, via WebFetch summary)
- Android: official "GUI binding" in `examples/llama.android` (Kotlin facade `AiChat` / `InferenceEngine`, tokens collected in a Kotlin `Flow`, GGUF metadata reader). "This Android binding supports hardware acceleration up to `SME2` for **Arm** and `AMX` for **x86-64** CPUs", auto-detecting host features. It is an example project to import into Android Studio; no Maven coordinates are documented. NDK cross-compile uses `-DANDROID_ABI=arm64-v8a -DANDROID_PLATFORM=android-28`. Source: https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/android.md (accessed 2026-10-11)
- Android GPU/NPU: OpenCL backend targets Qualcomm Adreno; verified Adreno 750, 810, 830, 840 (Snapdragon 8 Gen 3, 7s Gen 3, 8 Elite, 8 Elite Gen 5) and Windows 11 Arm64 on Snapdragon X Elite / X2 Elite (Adreno X1-85, X2-90). "A6x GPUs in phones are likely not supported due to the outdated driver and compiler." Source: https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/backend/OPENCL.md (accessed 2026-10-11)
- Hexagon NPU backend builds via the Qualcomm Snapdragon toolchain Docker images (Hexagon SDK 6.6.0.0) and installs per-generation HTP libraries `libggml-htp-v73/v75/v79/v81.so`; the doc covers Android and Windows-on-Snapdragon. Source: https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/backend/snapdragon/README.md (accessed 2026-10-11). The llama.rn README labels its Hexagon path "Experimental" and says "Qualcomm SM8450+ (8 gen 1 or newer) devices are currently supported & tested". Source: https://raw.githubusercontent.com/mybigday/llama.rn/main/README.md (accessed 2026-10-11)
- Vulkan on Android is flagged unsafe on some drivers by a downstream binding: Pixel 9 Pro (Mali-G715) wrong text for prompts over about 32 tokens in one batch; Galaxy A53 (Mali-G68) crashes while loading; Galaxy S24 (Adreno 750) crashes on first generation; "Keep `auto` or `cpu` unless Vulkan has been validated on your target devices." Source: https://llamadart.leehack.com/docs/platforms/support-matrix (accessed 2026-10-11)
- Streaming and structured output (llama-server): `stream: true` gives per-token SSE; `grammar` (GBNF) and `json_schema` constrain output; OpenAI-compatible `/v1/chat/completions` and `/v1/models`; `--api-key`. Tool calling: "adds support for OpenAI-style function calling ... `llama-server` when started w/ `--jinja`", native handlers for Llama 3.x, Hermes 2/3, Qwen 2.5, Mistral Nemo, Command R7B, GPT-OSS and others, with a "Generic" fallback for other templates. Sources: https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md and https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/function-calling.md (accessed 2026-10-11)
- Supported model families: not a closed set; the built-in chat template list includes gemma, llama2/3/4, phi3, phi4, qwen via chatml, mistral variants, granite 4.0/4.1, gpt-oss, deepseek, smolvlm and others. Source: llama-server README `--chat-template` row (accessed 2026-10-11)

Sources: https://dl.google.com/dl/android/maven2/com/google/ai/edge/litertlm/litertlm-android/0.18.0/litertlm-android-0.18.0.aar and https://dl.google.com/dl/android/maven2/com/google/ai/edge/litertlm/litertlm-jvm/0.18.0/litertlm-jvm-0.18.0.jar (accessed 2026-10-11)

Source (third-party binding docs, secondary): https://llamadart.leehack.com/docs/platforms/support-matrix (accessed 2026-10-11). Consistent with the missing `windows-aarch64` native in the official JVM jar (measured above).

### F4. Published performance figures

Vendor/project-published ExecuTorch benchmark on OnePlus 12 (16 GB RAM), 64-token input, XNNPACK with KleidiAI: Llama 3.2 1B SpinQuant decodes 50.2 tokens/s, TTFT 0.3 s, prefill 260.5 tokens/s, `.pte` 1,083 MiB and RSS 1,921 MiB. 3B SpinQuant decodes 19.7 tokens/s, TTFT 0.7 s, prefill 89.7 tokens/s, `.pte` 2,435 MiB and RSS 3,726 MiB. These are flagship results and cannot establish the mid-range target budget or full 100-card Oracle prompt latency. Source: https://github.com/pytorch/executorch/blob/main/examples/models/llama/README.md (accessed 2026-10-11).

Comparable named-device Android and Windows throughput, TTFT and memory for llama.cpp, LiteRT-LM, ONNX GenAI, MLC, Foundry and Phi Silica are UNVERIFIED in this pass: inspected runtime docs, searched official Android benchmark sources and found no common workload covering the target devices. Apple-only llama.cpp benchmark tables were excluded from Windows estimates. Source searched: https://github.com/ggml-org/llama.cpp/discussions/4167 (accessed 2026-10-11). No hardware measurement was run. Gate 2 should define a 6/8 GB Android device and 16 GB Windows device, pin model/hash/backend/context, measure cold/warm load, 1K/2K/4K prompt TTFT, decode rate, peak RSS, cancellation and sustained thermal behavior. This is a proposed validation plan, not a performance finding.

### F7. Model download manager facts

- Hugging Face offers revision-pinned downloads and metadata containing size, commit hash, ETag and redirected location. Documented ETag semantics are git SHA-1 for Git files and SHA-256 for Git LFS files. Xet uses a separate content-addressed storage mechanism; never treat every ETag or Xet identifier as SHA-256 of the reconstructed model. Sources: https://huggingface.co/docs/huggingface_hub/en/package_reference/file_download and https://huggingface.co/docs/hub/xet/index (accessed 2026-10-11).
- Direct CDN HTTP Range behavior for each proposed model artifact is UNVERIFIED: no HEAD/206 probes could be repeated because the shell proxy is unavailable; web page retrieval does not prove Range support. GitHub release asset Range behavior and checksums for all F1 native packages are similarly UNVERIFIED. ExecuTorch Android guide links `.sha256sums` for historical releases, demonstrating published checksums for those artifacts only. Source: https://docs.pytorch.org/executorch/stable/using-executorch-android.html (accessed 2026-10-11).
- Recommended manager contract, an implementation proposal: manifest with immutable revision, model license, exact bytes, format, minimum tested RAM and whole-file SHA-256; temporary partial file, byte offset and validator persisted; resume only when response is 206 with matching Content-Range/validator; restart safely on 200 or changed artifact; re-resolve expired redirects; verify checksum before atomic activation; preserve previously active model. Wi-Fi-only/cancel and free-space estimate must precede download. Range semantics source: https://www.rfc-editor.org/rfc/rfc9110.html#name-range-requests (accessed 2026-10-11; normative document not retrieved in this pass, details UNVERIFIED pending implementation review).

## Options

1. llama.cpp shared baseline: largest practical GGUF choice and straightforward C ABI, custom S1 JNI adapter, existing S2 community bridge. CPU fallback first; separately validated Windows GPU and Android acceleration. Supported by F1.1/F5, with resume caveats on versions and size.
2. LiteRT-LM secondary adapter: strongest official Kotlin API/tool loop, curated format, different model files and uncertain Windows ARM64 package coverage. Supported by F1.2/F5; latest versions remain unverified.
3. ONNX GenAI/Foundry Windows acceleration adapter: especially useful to C# stacks; retain independent Android baseline until packaging is proven. Supported by F1.3/F2/F5.
4. MLC or ExecuTorch: hardware-focused export pipeline adds compilation/model conversion cost. ExecuTorch has concrete Android performance evidence, but Windows parity and cross-stack deployment remain verification work. Supported by F1.4/F1.5/F4.

These are judgments from cited findings, not new platform guarantees.

## Recommendation

Recommend llama.cpp/GGUF as the baseline runtime on Android and Windows, with a runtime-neutral streaming/cancel/tool interface and optional LiteRT-LM adapter for S1. Start download catalog evaluation with Apache-licensed Qwen3-0.6B and Qwen2.5-1.5B, not a promised model quality threshold. Choose S1 or S2 using R-01's whole matrix; this criterion does not justify abandoning Kotlin fallback. Validate native package ABI, long deck prompt quality and memory on target devices before dependency pinning. This recommendation follows F1, F3 and F5 source evidence (accessed 2026-10-11).

## Risks

- Hardware backend support is device/driver-specific; keep CPU fallback and explicit capability testing. Sources: Android/backend docs in F1.1 and MLC guide in F1.4 (accessed 2026-10-11).
- Flagship 64-token benchmark evidence does not establish affordable-phone full-deck TTFT or memory. Source: ExecuTorch benchmark in F4 (accessed 2026-10-11).
- Runtime license does not license its weights; Gemma/Llama/Foundry terms remain artifact-specific open verification items. Sources: F3.1 (accessed 2026-10-11).
- Exact stable releases, APK/MSIX deltas, host Range/checksum behavior and Windows ARM64 adapter builds remain explicitly unverified. The research is complete as an evidence inventory; these items require release metadata/build/device checks before the product promise. Sources and attempted methods: F1, F6 and F7 (accessed 2026-10-11).
